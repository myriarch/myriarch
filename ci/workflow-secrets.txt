# Secrets that deployment jobs may read; the workflow policy check (ci/check-workflows.py, rule R10) allows nothing else.
#
# The workflows run without secrets. A job may read a secret only when all three conditions hold:
#
#   1. This file lists the job and the secret, one line per secret in the form
#
#        <workflow file> <job id> <NAME>
#
#      for example `deploy.yml publish PUBLISH_TOKEN`.
#   2. The job declares `environment:` at job level (a name, or a mapping with `name:`). The job then runs only after the
#      protection rules of that environment (required reviewers, deployment branches) are met, and the secret is an
#      environment secret of it.
#   3. The secret is the whole value of a key in the `env:` mapping of that job or of one of its steps, written exactly
#      `KEY: ${{ secrets.NAME }}`. It never appears in `run:` text, `with:`, `if:`, the workflow-level `env:`, a flow
#      mapping, a block scalar, index syntax (`secrets['NAME']`) or a function (`toJSON(secrets)`), and a workflow never
#      uses `secrets: inherit`.
#
# Each line needs a review of the job: which secret, why the job needs it, which environment protects it, and that fork
# pull requests receive no secrets (GitHub passes none to a workflow that a fork triggers). A line whose workflow file, job
# or secret does not exist (any more) fails the check, and so do a malformed and a duplicate line.
#
# The file is empty on purpose.

### Upgrade notes

- **`install-linux.sh` no longer requires `--collector-version`.** Without `--server` and without the option, the installer installs the version that its release was tested with (the `OTELCOL_VERSION` of `ci/versions.env`) and says so; `--collector-version latest` asks GitHub for the newest release, on request only, because that version is not the one that was tested. Before, the missing option stopped the run with `option_missing`. With `--server` the version comes from the plan. `install-windows.ps1` still requires `-CollectorVersion`. A script that relied on the error now installs the tested version: pass the version of your fleet explicitly, or use `--server`.

### Added

- **Installation from the server on Linux.** `install-linux.sh --server <url> --token-file <file>` takes the versions, the OpAMP endpoint and the artifacts from the server instead of from the operator ([ADR-0046](docs/adr/0046-host-installation-from-the-server.md)). It asks `POST /api/v1/install/plan` (the token only as a request header, read by `curl` from standard input) and reads the plan strictly as data: known keys only, each value against a pattern, at most 64 lines and 8 KiB, URLs of the origin of `--server` only, https only, redirects only to the same origin. Collector and supervisor are downloaded with the install grants of the plan and verified with SHA-256 and their Sigstore bundle against an identity that the installer builds itself; the verifier is the `myriarch-updater` of the installer bundle (`verify-bundle`), so the host needs no `cosign`, and nothing runs before its check. A plan that the server is still preparing is awaited (`--plan-wait`, default 15 minutes, after `Retry-After`). New error codes `plan_failed`, `plan_invalid`, `plan_rejected` (with the code of the server) and `plan_unavailable`, each with the next step; `https_required`, `conflicting_install` and `supervisor_missing` apply as before. The commands that the server renders for Linux run unchanged with the script (`--server`, `--token-file`, `--ca-file`, `--fleet`, `--insecure` and the site options). See [Connect a host](docs/tasks/connect-a-host.md#one-command-install-a-linux-host-from-the-server) and [Installing a Linux host from the server](docs/operations/troubleshooting.md#installing-a-linux-host-from-the-server).
- **Host end-to-end test: scenario `one-command`.** `scripts/host-e2e/linux.sh one-command` creates a token at run time, renders the command through `POST /api/v1/install/commands`, runs it unchanged as root on a fresh runner and checks a healthy agent in the expected fleet at its target version, a configuration rollout, a version update through the updater with a rollback and the retry, and the uninstallation with the proof that nothing is left. The workflow `host-e2e.yml` runs it after `manual` (the bundle is built from the commit and served from a directory by the development server), the path filter names `internal/install/**` and the parts of the bundle, and a manual run takes the input `release_tag` (for example `v0.2.0-rc.1`) to install from the published, keyless verified installer bundle of that release instead. The token is masked in the log, and the upload takes an allow-list of files, never the token file or the rendered command.

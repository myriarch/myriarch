## Unreleased

First public release. The sections below describe what the project ships; the history before publication is in the Git log.

### Added

**Defaults.** Without configuration, `myriarchd` behaves neutrally:

| Area | Default |
|---|---|
| Maintenance window time zone | `rollouts.defaultTimezone` is `UTC` |
| Artifact prefetch | `artifacts.prefetchPlatforms` is empty |
| UI language | English, with detection from the browser language (`ui.defaultLanguage`, `ui.languages`) |
| Login path in `serve` mode | `myriarchd serve` requires `auth.oidc.enabled` or `auth.bootstrapAdmin.enabled` |
| Webhook and AWX targets | `executors.allowedWebhookHosts` is empty and refuses every target (fail closed, in every mode) |
| Helm chart ingress | `ingress.enabled` is `false` |
| Helm chart GitOps | `config.gitops.enabled` is `false` |
| Helm chart network policy | No fixed ingress-controller or monitoring namespace; port 8080 is open to the pods of the release namespace (`networkPolicy.ingress.from` and `networkPolicy.metrics.from` widen it) |
| Helm chart storage | `emptyDir.sizeLimit` 4Gi, `persistence.size` 10Gi, `config.artifacts.maxCacheBytes` 3 GiB |
| Helm chart download tokens | `config.auth.downloadTokenSecretFile` is empty (key stored in the database, shared by all replicas) |

- **Time zone.** Rollout policies whose maintenance windows follow the agent's time zone (`timezone` empty or `agent`) and that set no `spec.defaultTimezone` fall back to `rollouts.defaultTimezone` for agents without a valid time zone attribute. `myriarchd` logs one warning at startup that lists such policies and names the effective default, and the rollout engine logs the same warning once per policy the first time it plans a rollout with it.
- **Prefetch.** The prefetch of new target versions adds the platforms of the members of updater fleets. An explicit prefetch request (`POST /artifacts/actions/prefetch`) that names no platforms uses `artifacts.prefetchPlatforms`; if that is empty too, it uses the distinct platforms of the connected collectors of the fleets that use the requested distribution. The request fails with 422 when that set is empty as well.
- **UI language.** The UI picks the language in this order: the choice stored in the browser, the first supported browser language (`de-AT` matches `de`), the server default `ui.defaultLanguage`, English. The first day of the week in the date pickers follows the language.
- **Fail-closed allowlist.** An empty `executors.allowedWebhookHosts` refuses every webhook and AWX target without sending a request.
- **Login path.** `myriarchd serve`, `myriarchd config validate` and `myriarchd migrate` fail with a clear error when neither single sign-on nor the bootstrap admin is configured. The development login exists only in `myriarchd dev` ([ADR-0025](docs/adr/0025-login-without-enterprise-idp.md)). The Helm chart enables the bootstrap admin by default (`bootstrapAdmin.enabled: true`) and generates a one-time token.
- **Feature-gated secret files.** `myriarchd` reads a `*File` setting only while its feature is active: the OIDC secret and certificate files while `auth.oidc.enabled`, the bootstrap files while the bootstrap admin is active, the GitOps credentials and `gitops.webhookSecretFile` while `gitops.enabled`, and `releases.tokenFile` while `releases.enabled`. The chart renders these file paths only for active features.
- **Interfaces.** The binaries are `myriarchd` (server), `myrctl` (CLI), `myriarch-updater` (host updater) and `myriarch-sim` (simulator); the short CLI alias `myr` is documented in `docs/reference/cli/myrctl.md` and not shipped. The GitOps `apiVersion` is `myriarch.dev/v1alpha1`. The images are `ghcr.io/myriarch/myriarch` and `ghcr.io/myriarch/myriarch-updater`, and the Helm chart is `deploy/helm/myriarch` ([ADR-0015](docs/adr/0015-project-name-and-naming-scheme.md), [ADR-0029](docs/adr/0029-host-under-the-myriarch-organization.md)).
- **Web UI.** The UI shows the project logo (the tetractys mark) in the favicon, the header, the login page and the loading screen, and serves `favicon.svg`, `favicon.ico` and `apple-touch-icon.png`. The logo files and the brand guide are in `assets/brand/`.
- **Rollout page.** The rollout targets list shows targets with running work first (in progress and verifying, then waiting for a maintenance window, failed and rolled back, pending, succeeded, skipped, cancelled) and can switch to the wave order. A wave card shows "Approval required" only before the approval, and "Approved" after it. The wave percentage is labelled as the cumulative share of all targets. Progress bars draw pending targets as empty track and use yellow only for targets waiting for a maintenance window.
- **API.** `GET /api/v1/rollouts/{id}/targets` accepts `sort=wave` (default, unchanged order: wave, hostname, agent ID) or `sort=activity`, and `agent=<agent ID>` to return the target of one agent. The open detail view of a target on the rollout page follows its target when the row moves to another page.
- **Examples and tooling.** `myriarchd dev` reads `examples/quickstart` by default (`--gitops-dir`); `make dev`, `make validate-examples` and `ci/verify-gitops.sh` use it. `make sim`, `myriarch-sim` and the compose and image examples use `examples/sim/mixed-fleet.yaml`. The e2e load run is `E2E_AGENTS=1000 scripts/e2e.sh`. The crane image scripts require `IMAGE_REPO`, read the OCI labels from `ci/image-labels.env` and derive the source label from `SOURCE_URL` or the git remote. The mirror image uses the public busybox base, pinned by digest.
- **Installers.** Every error and warning line of the installers carries a stable code: `[myriarch-install] ERROR [<code>] ...`; the catalog is in `deploy/scripts/install-linux.sh` and `deploy/windows/README.md`. Helm `fail` messages start with the value path, for example `config.server.trustedProxies: ...`.
- **API and web UI version.** The version of the REST API (`info.version`) and of the web UI package follows the release version instead of `1.0.0-alpha.1` ([Releasing](docs/releasing.md)).
- **Installer prerequisites.** `install-linux.sh` checks for `gzip` next to `tar` and stops with `[tool_missing]` that names the tool, instead of reporting a valid collector archive as `[archive_invalid]`: GNU `tar` runs `gzip` to unpack the `.tar.gz` archives.
- **Keyless updater verification.** The installers verify the updater through the keyless Sigstore bundle of the release instead of a key: `--updater-checksums-url` (`-UpdaterChecksumsUrl`) downloads `checksums.txt` and `checksums.txt.sigstore.json` (`--updater-bundle-url` / `-UpdaterBundleUrl` for another location), verifies the bundle against the identity `release.yml@refs/tags/v<version>` of this repository with the issuer `https://token.actions.githubusercontent.com`, and takes the hash of the updater from the verified file. The version comes from `--updater-version` (`-UpdaterVersion`) or from the file name `myriarch-updater_<version>_<os>_<arch>` of `--updater-url`; if both are given they must agree (`option_conflict`). New error codes `option_removed` and `sigstore_verifier_outdated`. `--updater-sha256` stays for hosts without a verifier.
- **Language guard.** `make check-local` runs the language guard strictly for `cmd`, `internal`, `scripts`, `ci`, `contrib`, `deploy`, `examples`, `web/src`, `docs`, `.github` and the root Markdown files. `LANGUAGE_GUARD=warn` makes it report-only and `LANGUAGE_GUARD=off` skips it.
- New top-level configuration section `ui` with the options `ui.defaultLanguage` (default `en`) and `ui.languages` (default empty, meaning every language the UI ships). Both are validated at startup: language tags must match `^[a-z]{2,3}(-[A-Za-z0-9]{2,8})*$`, must not repeat, and `ui.defaultLanguage` must be one of `ui.languages` when that list is set.
- The audit entry `artifact.prefetch` records the resolved platforms (`platforms`) and where they came from (`platformsSource`: `request`, `config` or `connected`).
- The public endpoint `GET /api/v1/auth/config` returns the new field `ui` (`defaultLanguage`, optional `languages`). It contains no secrets.
- The UI derives its languages from a locale registry (`web/src/i18n/locales.ts`); the language menu and the profile settings offer the shipped languages, restricted by `ui.languages`. Entries of `ui.languages` may carry region subtags (`de-DE`); like the browser language and `ui.defaultLanguage`, they match a shipped language by the full tag or the primary subtag.
- **Bootstrap admin.** `auth.bootstrapAdmin` (`enabled`, `username`, `passwordHashFile`, `tokenFile`, `keepWithOidc`) configures a break-glass administrator for the initial setup and emergencies. Credentials come from files only: a bcrypt hash for password sign-in, a random token for one-time token sign-in (single use, cluster-wide marker, rotated by rewriting the file). The account is active unless OIDC is enabled without `keepWithOidc`; the configuration is the only source of truth, and `PATCH /users/{id}` on the account answers `412`. Sign-in is rate limited per client address (IPv6 per /64) and per account (per replica, one verification at a time), deactivating the account revokes the API tokens it created, every attempt is audited, and the UI shows a banner on every page while such a session is open. The revocation converges across restarts: the steps of an account run in one transaction, every start removes what an already disabled account still holds (`auth.bootstrap.deactivate` with `alreadyDisabled: true`), and an account that becomes active again loses the sessions and tokens of its earlier life before it is enabled (counted in `auth.bootstrap.activate`). The account backoff is shared by every client, so network access to `POST /api/v1/auth/bootstrap-login` should be restricted; restarting the pod clears the counter. See `docs/operations/authentication.md`.
- **IPv6 clients.** The failure limiters of the invalid bearer tokens and of the dev login count IPv6 clients per /64 prefix, like the bootstrap sign-in.
- **AWX API prefix.** `spec.awx.apiPrefix` selects the API path of an AWX or Ansible Automation Platform executor (default `/api/v2/`; Ansible Automation Platform 2.5 and later: `/api/controller/v2/`). `myrctl validate` and the syncer check the value (`executor_invalid`).
- **OpenShift.** `openshift.enabled` (`true`, `false` or `auto`) switches the chart to an OpenShift profile: no fixed UID, GID or fsGroup, a Route (`openshift.route.*`), the router namespace in the network policy and the OpenShift DNS pods. `auto` detects `security.openshift.io/v1`; `helm template` without `--api-versions security.openshift.io/v1` renders the standard profile.
- **Helm chart.** `examples/quickstart-dex.yaml` with `examples/dex/dex.yaml` (Dex as demo identity provider, OIDC enabled, bootstrap admin off); `resources` set `ephemeral-storage` requests and limits; the PodDisruptionBudget renders only with `replicaCount > 1`; `secretChecksum.enabled` (default) rolls the pods when a mounted Secret changes (`checksum/secret`, derived from the uid and resourceVersion of the Secrets, not from their content); `helm template` fails when neither OIDC nor the bootstrap admin is enabled; the egress rule includes the Git SSH port (22, or the port of an `ssh://` URL) when GitOps uses SSH, `networkPolicy.egress.extraPorts` and `extraRules` extend it, and `networkPolicy.egress.dns` sets the DNS rule; `networkPolicy.ingress.allowSameNamespace` and `ingress.allowWithoutTls` / `allowWithoutTrustedProxies` make the safety checks explicit.
- `myriarchd auth hash-password [--cost N]` reads a password from standard input (12 to 72 bytes, cost 10 to 14, default 12) and prints a bcrypt hash for `auth.bootstrapAdmin.passwordHashFile`.
- **Declarative enrollment tokens.** `opamp.enrollmentTokens[]` (`name`, `tokenFile`, `labels`, `expiresAt`) provisions enrollment tokens from files at start. Only the SHA-256 hash and the display prefix are stored; the start is idempotent, a revoked token is never re-activated, and a token that is removed from the configuration is not revoked automatically (a warning names it). A change of labels or expiry reaches all replicas at once. Such tokens show `createdBy: config` in `GET /enrollment-tokens` and a badge in the UI.
- **Secret file permissions.** Outside Windows the server logs a warning at start for every secret file that other users of the host can read or write (mode bits 0007): the bootstrap admin and enrollment token files, the database DSN file, the OIDC client secret and key files, the TLS key file, the download token secret, the GitOps token, SSH key and webhook secret files, the release tracker token, the artifact mirror credentials, the notification URL and secret files and the registered executor secrets (`executors.secrets`; other files in `executors.secretDir` are not checked). Only the file mode is examined, the content is never read. The message names the setting and the path, never the content. Files of features that have a switch (OIDC, GitOps, release tracker) are checked only while the feature is active; notification channels, the artifact mirror credentials and executor secrets have no switch and are checked when they are configured.
- **Vendor-neutral OIDC.** `auth.oidc.nameClaim` (default `name`) and `auth.oidc.emailClaim` (default `email`); `auth.oidc.roleMapping.users` maps single users by `sub:<subject>` or `email:<address>` (the e-mail form requires `email_verified: true` and `emailClaim: email`, because the flag covers only that claim); `groupsClaim` also accepts an object claim and uses its keys (Zitadel project roles). OIDC callbacks reject the reserved subject prefixes `local:` and `bootstrap:`.
- **Provider hints.** `internal/configload/providers.go` holds a table with issuer checks and warnings for Microsoft Entra ID, Keycloak, Okta, Dex and Google. `docs/operations/authentication.md` has recipes for Keycloak, Dex, Microsoft Entra ID, Okta, authentik, Zitadel and Google.
- **API.** `POST /api/v1/auth/bootstrap-login` (operation `bootstrapLogin`, public). `GET /auth/config` returns `bootstrapPasswordEnabled` and `bootstrapTokenEnabled`, `GET /system/info` returns `features.bootstrapAdmin`, and `authMethod` and the user `provider` can be `bootstrap`. `PATCH /users/{id}` can answer `412`.
- **Audit events.** `auth.bootstrap.login` (success and failure with `reason`, rate limiting with `limitedBy`), `auth.bootstrap.activate` and `auth.bootstrap.deactivate` (actor system); declarative tokens write `enrollment_token.create` and `enrollment_token.update` with `source: "config"`. The metric `myriarch_auth_logins_total` has the method `bootstrap`.
- **Database.** Migration `00005_bootstrap_admin.sql` allows the user provider `bootstrap` (expand only). The latest schema version is 5.
- **Helm chart.** The top-level values `bootstrapAdmin.*` (generated one-time token Secret `<fullname>-bootstrap` or an existing Secret with a token or a bcrypt hash) and `enrollmentTokens[]` (generated or existing Secret per token, mounted below `/etc/myriarchd/enrollment`) render the configuration above. `NOTES.txt` explains how to read the generated token without printing it. `oidcFromEnvironment: true` declares that single sign-on is switched on by environment variables (`MYRIARCH_AUTH_OIDC_ENABLED` in `extraEnv`), which the chart cannot read: the login path check passes, the bootstrap Secret is mounted only with `keepWithOidc`, and the `config.auth.oidc.*File` fields stay rendered.
- **Web UI.** The login page offers the bootstrap admin with password or token (collapsed behind "Use the bootstrap admin" next to other methods, expanded when it is the only one); the users list shows the account as managed by configuration.
- `examples/quickstart/` is a small, generic GitOps repository (fleets `linux-hosts`, `windows-hosts`, `k8s-gateway`; site types `edge`, `datacenter`, `cloud`) with a version policy `canary-then-all` whose maintenance windows use the site-local time zone and UTC, and a config policy `config-canary`. A README describes it. `examples/sim/mixed-fleet.yaml` is the matching simulator profile (1000 agents: 400 / 200 / 300 / 100 and 900 myriarch-updaters).
- **Licensing.** The repository has the Apache-2.0 `LICENSE`, an SPDX header in every source file and a REUSE 3.3 configuration (`REUSE.toml`, `LICENSES/`); the gate `licenses` of `make check-local` checks the headers, runs `reuse lint` and detects drift of `THIRD_PARTY_NOTICES`. `THIRD_PARTY_NOTICES` lists the licenses and notices of the Go modules and web UI packages in the binaries and is generated by `scripts/gen-third-party-notices.sh`; every distinct license text is printed once and referenced by the components that ship it, and the generator fails when the file exceeds 1,000,000 bytes. It is part of every release archive and container image, `myriarchd` serves it with `LICENSE` at `/licenses` without login, and Settings > System links both. The OpenAPI document, `web/package.json` and the Helm chart declare Apache-2.0. `myriarch-updater licenses [--third-party]` prints both texts from the binary, so the bare updater binary carries them; the Helm chart contains `LICENSE`; the container images set `org.opencontainers.image.licenses`; `ci/build-release.sh release` checks the notices and the release licenses before it builds. The licenses of dependencies with a package list in `ci/license-overrides.txt` fail closed when a new package of the module is linked.
- **Website.** The sources of the project website (myriarch.dev) live in `website/`: Hugo extended with the Docsy theme, built from `docs/` and the root Markdown files without copying them, with offline search, light and dark mode, no third-party requests and no cookies ([ADR-0031](docs/adr/0031-website-with-hugo-and-docsy.md)). `make website`, `make website-serve`, `make website-preview` and `make website-check` build, serve and check it, and the new gate `website` of `make check-local` runs the build, the link check, markdownlint and the checks of `website/scripts`. Hugo, Dart Sass and lychee are pinned in `ci/versions.env` with SHA-256 values. The site has a landing page with screenshots of the web UI, the REST API reference, the Helm chart, GitOps template and brand pages, a project section with a FAQ, and placeholder pages for documentation that is still being written. The documentation is grouped as getting started, how-to guides, concepts, reference, operations and security. The license texts of the shipped third-party components are published under `/licenses/`, and the gate checks that every link into the repository names an existing path.
- **Website.** The REST API reference is generated from `api/openapi.yaml` (`make docs-gen`, checked for drift): one page per tag and a data types page with the site's theme, dark mode and search, and no JavaScript. It replaces the Redoc viewer.
- **Website.** The mark on the landing page plays a short rollout once on load (control plane, canary, waves, full fleet) and ends on the unchanged mark; with reduced motion it is static.
- **Website.** `.github/workflows/website.yml` builds the site with the pinned tools, runs the website gate and deploys `website/public` as prebuilt static output to Vercel: production on pushes to `main`, protected previews (`noindex`) for pull requests from branches of the repository, never for forks. `WEBSITE_ENV=preview` builds with the production asset pipeline (minified, fingerprinted, no source maps) and only adds `noindex` and `Disallow: /`; previews use `WEBSITE_BASEURL=/`. A new check, `check-indexing.py`, verifies both modes. The setup (Vercel project, the environments `website-preview` and `website-production`, domain records) is in `website/README.md`.

### Security

Fixes and hardening from the pre-publication security audit. The controls are described in `docs/security/model.md`; the limitations that remain are in its section "Known limitations".

- **GitOps source.** The clone always follows `gitops.repoUrl`: a changed URL with the same `gitops.cloneDir` no longer keeps applying the previous repository, and an existing clone whose origin differs is replaced.
- **HTTP listeners.** Every request has 60 seconds to deliver its body and an idle write timeout of 60 seconds (accepted event streams and handed-over WebSocket connections are exempt; a rejected request keeps both budgets), request headers are limited to 64 KiB on both listeners, `/readyz` caches the database check for 2 seconds and coalesces concurrent checks, and public state-changing routes (sign-in) require `Content-Type: application/json`.
- **Agent authentication.** The OpAMP connect limit uses one bucket per IPv6 /64 (IPv4-mapped addresses count as IPv4). Only well-formed enrollment tokens are looked up; unknown tokens are cached in a separate small cache, concurrent lookups are coalesced and lookups of uncached tokens are limited per replica (`429` with `Retry-After`). Token usage is written with one statement per token and flush.
- **Sign-in.** Failed OIDC callbacks are limited per client address (both OIDC endpoints refuse an address with an empty bucket), failures before a verified login state are audited at most once per minute and address, and responses of the identity provider are limited to 1 MiB. Group names are matched exactly (no case or Unicode folding) and e-mail entries ignoring the case of ASCII letters only: a mapping that relied on a different case of a group name has to use the exact name. The session cookie is named `__Host-myriarch_session` where cookies are Secure (production); existing sessions end with the upgrade. API tokens of local development accounts are refused where the development login is off.
- **API tokens.** New setting `auth.apiTokenMaxTtl` (default 90 days; `0` means unlimited and logs a warning): a token created without `expiresAt` gets the maximum, a later `expiresAt` is refused with `422`, and older tokens stop working. Existing tokens without an expiry stop working 90 days after their creation. The token list and the web UI show the effective expiry. Offboarding a user at the identity provider does not end API tokens: disable the user in myriarch.
- **Configuration checks.** Production refuses `server.trustedProxies` ranges that cover every address and a zero `artifacts.downloadTokenTtl`, and refuses unanchored `artifacts.verify.certificateIdentityRegexp` patterns. It warns about `/metrics` on the main listener, a remote database connection without certificate verification, empty `artifacts.dir` and `gitops.cloneDir`, secrets set as literal values in the configuration file, credentials in `artifacts.proxyUrl` and very broad trusted proxy ranges. `myriarchd config print` redacts credentials in URL-valued settings. The development mode guard also covers `server.metricsListenAddr`. The removed constant `config.DefaultDataDir` was unused.
- **Outbound policy.** Only the exact proxy address is exempt from the address check and only in the transport that uses it (`ALL_PROXY` exempts nothing), more special-purpose ranges are blocked (IPv4-compatible IPv6, Teredo, the discard prefix, `192.88.99.0/24` and the IPv4 documentation ranges; `outbound.allowedCidrs` can open them), and address literals and `localhost` in a request URL are refused locally when a forward proxy applies.
- **Secret files.** The start-up check also covers files below `executors.secretDir` that are bound in `executors.secretFileHosts` and the directory itself, and operator-chosen executor secret files are read as regular files of at most 1 MiB. `myriarch-updater` warns about loose modes of its token file.
- **Error responses.** Database errors that become 4xx answers no longer carry the operation name, constraint names or driver text; they are logged with the request ID.
- **Installers and units.** The certificate identities passed to `cosign` and `verify-bundle` are bound to the requested version. The Linux installer requires `curl` unless `--insecure` is given, extracts archives without owner and mode, and copies `--ca-file` to `/etc/myriarch/ca.pem` (the configuration files now reference that path; the option takes an absolute path). The Windows installer prefers the verified updater over `cosign.exe` from `PATH`, creates its work directory with a protected DACL, hashes verified files again after copying, and applies and verifies a fresh ACL on the service key before it writes the token (`Set-ServiceEnvironment.ps1` does the same). `otelcol-supervisor.service` drops all capabilities and sets further hardening directives. Both updater and `verify-bundle` refuse unanchored identity patterns.
- **Installers verify the keyless release bundle (breaking).** `--signing-key`, `--updater-checksums-sig-url`, `-SigningKey` and `-UpdaterChecksumsSigUrl` and the key-signed `checksums.txt.sig` were removed; using one fails with `option_removed`, and the message names the replacement (`--updater-checksums-url` with its bundle, `--updater-bundle-url`). The error codes `signature_invalid`, `signature_malformed`, `signature_verifier_missing` and `signing_key_invalid` no longer exist. The verifier of `checksums.txt` is `cosign` 3.0.4 or newer or an already installed `myriarch-updater`, and never the updater that is being installed; an older `cosign` stops the installation with `sigstore_verifier_outdated`, also for the collector and supervisor bundles. `--updater-checksums-url` cannot be combined with `--verify-signatures skip`. A `-Verifier` of the Windows installer must be in a directory that only administrators can write (`directory_unsafe` otherwise), a pre-release of `cosign` 3.0.4 counts as older, and on Linux every `--verifier` whose file name starts with `cosign` gets the version check. `-UpdaterSignerThumbprint` stays for private PKIs (a pinned thumbprint breaks at every certificate renewal). Known limitation: under App Control script enforcement the unsigned `install-windows.ps1` runs in Constrained Language Mode and fails; allow it by its hash.
- **Kubernetes.** The collector manifests set `automountServiceAccountToken: false`, the node agent changes only the top storage directory, and the Helm chart refuses to render inline secrets (`config.database.dsn`, `config.auth.oidc.clientSecret`, `config.gitops.webhookSecret`, `config.notifications.channels[].url`). The examples use `sslmode=verify-full`.
- **Dependencies and gates.** Go 1.27.2 and `golang.org/x/net` 0.60.0 fix the reachable vulnerabilities reported by `govulncheck`. New gates `vulncheck` (with an allowlist that records reason and review date) and `secrets` (gitleaks, `.gitleaks.toml`) in `make check-local`; the `go` gate also vets for Windows and compiles the updater tests for it. The security tests of the updater now compile for Windows.
- **Build and release.** Release builds ignore the tool cache and build the web UI from the tagged commit, the collector image defaults to the reviewed upstream digests and verifies the upstream binaries by default when it pushes, the `dev` image variant is refused for `ghcr.io/myriarch/*`, and the Docker build contexts exclude every git-ignored path.

### Build

- **Release images.** `ghcr.io/myriarch/myriarch` (`myriarchd`, `myrctl`, `myriarch-sim` and the example repositories) and `ghcr.io/myriarch/myriarch-updater` are image indexes for `linux/amd64` and `linux/arm64`, built `FROM scratch` with one layer from the linux archives of the release build instead of from a second compilation. They run as user and group 65532, hold the license files under `/usr/share/licenses/myriarch/` and carry the OCI labels in the platform configs and the index annotations. `IMAGE_SOURCE=dist IMAGE_KIND=server|updater scripts/build-image-crane.sh` writes a deterministic OCI layout (the same archives give the same uncompressed layers, and the same digests with the same zlib) and one SPDX SBOM per platform; `ci/release/push-images.sh` pushes a layout by digest, never sets a tag and verifies the digest it pushed. See `deploy/README.md`.
- **Server image content and data directory.** The published server image carries `myriarchd` (entrypoint), `myrctl` and `myriarch-sim` in `/usr/local/bin` and the example repositories `/opt/myriarch/examples/quickstart` and `/opt/myriarch/examples/sim`, so a Compose quickstart or a first try needs no repository checkout. All of it is read from the release archives and covered by `checksums.txt`: the `myriarchd` archive now also holds `examples/quickstart`, the builder takes `myrctl` and `myriarch-sim` from their own archives, and it refuses archives whose license files differ. The image creates the empty data directory `/var/lib/myriarchd` (0750, owned by 65532:65532), so a named volume, an `emptyDir` or a PVC mounted there works for the non-root user and the artifact cache survives restarts. `deploy/docker/myriarchd.Dockerfile` and the image built from source follow the same contract, and the development Compose file mounts a named volume at that path. The updater image needs no state directory (container mode keeps it on the volume of the collector image).
- **Image user.** The image that `scripts/build-image-crane.sh` builds from the work tree runs as user and group 65532 (it was 1001), like the Helm chart. It refuses `ghcr.io/myriarch/*`: those repositories are written only by the release workflow.
- **Updater trust store.** `myriarch-updater` embeds the Mozilla root CAs as a fallback, like the other binaries, so that the scratch-based updater image can verify TLS servers. The host trust store still wins.
- **Removed images.** `deploy/docker/myriarchd-release.Dockerfile` and `deploy/docker/myrctl.Dockerfile` are gone, together with `MYRCTL_BASE_IMAGE`. The project publishes no `myrctl` image; the binary is in the release archives, and the GitLab starter in `gitops-template/` says to build an image from it.
- **Collector image.** `deploy/k8s/collector/Dockerfile` can copy `myriarch-updater` from the published updater image (`--build-arg UPDATER_SOURCE=image --build-arg UPDATER_IMAGE=ghcr.io/myriarch/myriarch-updater@sha256:<digest>`). Container mode is beta and needs a self-built collector image until the collector chart of v0.2.0 (`docs/design/container-mode.md`, `ROADMAP.md`).
- Release builds omit the `devpg` build tag, so the embedded PostgreSQL (and its dependencies) is not linked. `myriarchd dev` in such a build needs `--dsn`; `make dev` and `make build` keep the tag. See `docs/development.md`.
- `ci/check-release-licenses.sh` (part of `make check-local`) runs `go-licenses` over the release builds against a license allowlist; exceptions are documented in `docs/development.md`.
- The UI uses system font stacks instead of bundled web fonts, so the embedded UI ships no font files.
- `IMAGE_VARIANT=release scripts/build-image-crane.sh` builds the server image without `devpg` and without the OpenTelemetry release fixtures (`/opt/myriarch/release-fixtures`); the default `dev` variant keeps both.
- The in-process LRU caches use the internal `internal/lru` package, so `github.com/hashicorp/golang-lru` is not a dependency.
- **Continuous integration.** GitHub Actions runs the gates of `ci/check-local.sh` as jobs (`.github/workflows/ci.yml`), with a platform matrix for the Go tests (Linux amd64 and arm64 with a PostgreSQL service and `-race`, macOS with `-race`, Windows without `-race`), the release snapshot, a secret scan of the commits of a pull request and the script tests. The aggregate job `ci-ok` is the only required check. `.github/workflows/e2e.yml` runs the end-to-end smoke test on pull requests and the load run and the UI version update test nightly. Only GitHub-owned actions pinned to a commit SHA are used, the token is read-only and the CI jobs have no secret; a deployment job can read an environment secret only when `ci/workflow-secrets.txt` lists it, the job declares an `environment:` and the secret is passed as `KEY: ${{ secrets.NAME }}` in an `env:` ([ADR-0032](docs/adr/0032-continuous-integration-on-github-actions.md)).
- **Workflows gate.** `make check-local` has a gate `workflows`: `actionlint` (pinned in `ci/tools/actionlint`) and the policy check `ci/check-workflows.py`, which also verifies that every gate has a CI job and reads workflow files and local actions with the extension `.yml` as well as `.yaml`. The gates `go` (vet for macOS) and `helm` (schemas of Kubernetes 1.30.0 and 1.34.12) check more; `GO_TEST_RACE`, `GO_TEST_DEVPG`, `GO_TEST_PERF`, `HELM_KUBERNETES_VERSIONS` and `CHECK_LOCAL_STREAM` select variants. The render budget of the server (5000 agents in under 5 s) is asserted only by a run of its own without `-race` (`PERFTEST=1`, `GO_TEST_PERF`), not inside the parallel `go test ./...`, and applies to the median of three renders.
- **Workflow policy for Scorecard and releases.** The policy check allows one third-party action, `ossf/scorecard-action`, pinned to a commit SHA and only in `.github/workflows/scorecard.yml`, job `analysis` (rule R1). Rule R12 holds that workflow to the shape the OpenSSF Scorecard API requires for published results (push to `main` and a schedule, one job, only `uses:` steps from a fixed list, exactly the permissions `contents: read`, `actions: read`, `security-events: write` and `id-token: write`, no secrets or caches). Rule R13 prepares `.github/workflows/release.yml`: a trigger for pushed `v*` tags only, no caches or local actions, the literal environment `release`, a `guard` job that every job needs, no Node.js, Go, pnpm, npm, goreleaser, make or similar build tool in a job with a write scope, `id-token`, `attestations` or an environment, no `if:` that tests job status and no `continue-on-error` that would defeat `needs:`, no script on standard input or foreign `shell:` in a privileged job, and an approval before every privileged job ([ADR-0033](docs/adr/0033-openssf-scorecard-as-the-only-third-party-action.md), which amends [ADR-0032](docs/adr/0032-continuous-integration-on-github-actions.md)).
- **Toolchain files.** `.node-version` pins the Node.js LTS release (24.21.0) for CI and local development; the `engines` of `web/` require Node.js 22.22.2, 24.15 or newer (`^22.22.2 || ^24.15.0 || >=26`). `pnpm format:check` (prettier) is part of the `web` gate and `make lint`, and `playwright-core` is a development dependency of `web/` for the UI smoke tests.
- **Dependency updates.** Dependabot (`.github/dependabot.yml`) now proposes weekly grouped updates for the GitHub Actions, the root Go module, the packages of `web/` and `website/` and the brand generator (`assets/brand/source`), and security updates for the CI tool modules (`ci/tools/*`); `docs/development.md`, "Dependency updates", says what each kind of pull request needs besides the update itself (the required DCO check passes Dependabot's commits as they are). The pins behind the open alerts are raised: Pillow 12.3.0 for the brand generator, which now needs Python 3.10 or newer (`BRAND_PYTHON` selects the interpreter), and the vulnerable packages of the CI tool modules and the website tooling. The stamp of a Go tool in `.cache/bin` now holds a digest of its `go.mod` and `go.sum`, so a raised requirement rebuilds the tool, also from a tool cache that CI restored from an older run (before, the old binary stayed until the tool version changed).
- **End-to-end test with the real supervisor.** `E2E_REAL=1 scripts/e2e.sh` downloads the upstream supervisor and `otelcol-contrib` of `OTELCOL_VERSION` for darwin and linux on amd64 and arm64 (previously darwin/arm64 only) and verifies both against the published SHA-256 on every run. With `E2E_REAL=1` or `E2E_UI=1` a missing prerequisite fails the run instead of skipping the step. `E2E_REAL_BASE_URL` replaces the download location.
- **Secret scan of commit ranges.** `SECRETS_SCAN_RANGE=<base>..<head> ci/secrets-scan.sh` scans the commits of a range with gitleaks.
- **Version source.** The file `VERSION` holds the next release tag without the `v` (`0.1.0-rc.1`), and `scripts/set-version.sh <version>` writes it together with every copy: the chart `version` and `appVersion`, `web/package.json`, `api/openapi.yaml`, the image tags of the production example and of the GitOps template; then it runs `make docs-gen` and `pnpm gen:api`. `ci/check-versions.sh` fails on drift (part of the `go` gate and `ci/check.sh`).
- **Release tag guard.** `ci/release/guard.sh` refuses a release tag that is malformed, lightweight, not on `main`, different from `VERSION` or one of its copies, without a `CHANGELOG.md` heading and entries (final tags) or without entries under "Unreleased" (rc tags), without a successful `ci-ok` check run, or against the Windows signing rule of `deploy/release/windows-signing.env` (a final tag with signing `off` needs the reviewed exception for exactly that tag).
- **Authenticode for Windows.** [ADR-0034](docs/adr/0034-authenticode-signing-of-windows-release-artifacts.md) decides how the Windows release files get Authenticode signatures: the SignPath Foundation is the target, an IV certificate with an HSM key in Google Cloud is the fallback (trigger, budget and privacy consequence are recorded), and the release workflow keeps no long-lived signing secret. Authenticode adds to the Sigstore signature of [ADR-0023](docs/adr/0023-keyless-release-signing.md) and never replaces it. The Windows files of v0.1.0 are unsigned under a reviewed exception for exactly that tag; verify them with cosign before you run them ([the security model](docs/security/model.md)).

### Documentation

The documentation is English ([ADR-0020](docs/adr/0020-english-as-project-language.md)) and has a new structure under `docs/`, with Hugo-compatible front matter on every page and a map in `docs/_index.md`.

- **Concepts** (`docs/concepts/`): GitOps, agents, blueprints, fleets, inventory, rollouts and executors.
- **Tasks** (`docs/tasks/`): step-by-step guides, for example connecting a host, validating a GitOps repository, rolling out a configuration change or a collector version, and simulating a fleet.
- **Getting started** and **operations**: `docs/getting-started/local-dev.md`, the production checklist and troubleshooting next to the existing authentication guide.
- **Reference** (`docs/reference/`): the GitOps schema reference with every kind, field, template function and issue code, and a command-line reference for all four binaries that `make docs-gen` generates from the command trees. `make docs-check` verifies that the generated files are up to date, that links resolve and that the front matter is valid.
- **Security model** (`docs/security/model.md`): trust boundaries, agent and user authentication, artifact verification, outbound connections and the Kubernetes network policy.
- **Verify releases** (`docs/security/verify-releases.md`, part 1): verify `checksums.txt` with its Sigstore bundle and the exact identity (`cosign verify-blob`), then the files with `sha256sum`; verify a downloaded archive before you run its installer, and `Unblock-File` only after that. `docs/tasks/connect-a-host.md`, `deploy/windows/README.md` and `contrib/enterprise-mirror/README.md` describe the new options, hosts without a verifier, upgrades, and mirrors that carry the keyless bundles unchanged.
- **Architecture and decisions**: `docs/architecture.md` and the decision records ADR-0001 to ADR-0029 in `docs/adr/`. `ROADMAP.md` holds the roadmap.
- **Developer guide** (`docs/development.md`) covers the server, the web UI and the documentation tooling.
- **Community files**: `README.md` (rewritten), `CONTRIBUTING.md` (DCO sign-off, AI-assisted contributions), `CODE_OF_CONDUCT.md`, `SECURITY.md` (private vulnerability reporting), `MAINTAINERS.md`, `GOVERNANCE.md`, `CONTRIBUTOR_LADDER.md`, `ADOPTERS.md`, `ROADMAP.md`, `AGENTS.md` (guidance for coding agents) and `CLAUDE.md` (a pointer to `AGENTS.md`), plus issue forms, a pull request template, `CODEOWNERS` and release note categories in `.github/`.
- The language guard of `make check-local` also covers `docs/`, `.github/` and the root Markdown files.

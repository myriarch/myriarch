# Changelog

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## Unreleased

### Upgrade notes

- **Back up the database before you upgrade from v0.1.0; going back to v0.1.0 means restoring that backup.** The upgrade applies new migrations (the first is `00006_schema_compat.sql`, expand only). v0.1.0 does not check the schema and its migration library accepts a database with higher versions, so it would start on a migrated database without a warning. A rollback to v0.1.0 is not supported ([ADR-0036](docs/adr/0036-database-schema-compatibility-and-rollback.md)). To prepare, take a backup of the PostgreSQL database (`pg_dump` or a snapshot of the managed database) before `helm upgrade` or before you start the new image. To go back, restore that backup and start v0.1.0 against it.
- **The server can refuse to start because of the database schema.** The database records a compatibility level, and `myriarchd serve` compares it with its own migrations. A schema that is incompatible with the binary is refused with an error that names the schema version and the levels, whatever `database.migrateOnStart` says. With `database.migrateOnStart: false`, a schema that lacks migrations of the binary is refused at once and the error names `myriarchd migrate`, where v0.1.0 started and failed later. A newer schema that is still compatible only logs a warning. If you run with `database.migrateOnStart: false`, run `myriarchd migrate` before you update the deployment; with the default `true`, nothing changes for you.
- **`myriarchd migrate` reads only the database settings and prints other lines.** The public URL, the login path and the secret files of other features are no longer needed or checked, and other sections of the configuration file are ignored; a file with `database.dsn` or `database.dsnFile` alone, or `MYRIARCH_DATABASE_*` variables alone, is enough. The output `schema version: N` is replaced by `schema version before: N`, `schema version after: N` and `compatibility level: N`. A script that reads the old line has to read `schema version after:`.
- **Helm chart: strict values schema.** `helm install`, `upgrade`, `template` and `lint` now validate the values against `values.schema.json` and refuse what the chart used to ignore or to accept without a word: a key that the chart does not know (a misspelled setting, also inside `config`), a value of the wrong type or in the wrong form (a number where the chart needs a string, a string such as `"false"` where it needs a boolean, a duration written as an integer such as `config.server.shutdownTimeout: 30` or with a unit that Go does not know such as `30d`, an image digest without `sha256:`, a registry with a scheme) and a secret as a value. The schema has no key for `config.database.dsn`, `config.auth.oidc.clientSecret`, `config.gitops.webhookSecret`, `config.notifications.channels[].url` or an enrollment token (`enrollmentTokens[].token`), and a Secret reference such as `enrollmentTokens[].key` must not have the form `myre_...`; use the `*File` settings and Secrets. `config.auth.bootstrapAdmin`, `config.opamp.enrollmentTokens`, `config.dev` and `config.auth.devLogin` were refused when the chart rendered and are now refused by the schema. **Before you upgrade,** run `helm lint` (or `helm template`) with your values file and the chart of this release and fix what it reports; the message names the path of the value. A release that was installed with `--set` or upgraded with `--reuse-values` has no values file: `helm get values <release> -n <namespace> -o yaml > current-values.yaml` writes its values. See [Install with Helm](docs/operations/install-helm.md#the-values-schema).
- **Helm chart: the registry of the image is a value of its own.** `image.registry` (default `ghcr.io`) holds the registry host, `image.repository` (default `myriarch/myriarch`) the repository without it, and `global.imageRegistry` replaces the registry, for example with a mirror. A repository that starts with a registry host (`registry.example.com/myriarch/myriarch`, the form of the values of v0.1.0, or `localhost:5001/myriarch`) is used unchanged, so values that set the full repository and the defaults render the same image as before. A repository **without** a registry host now takes `image.registry`: if you relied on the default registry of your container runtime for such a repository, set `image.registry: ""` or put the host into the repository. The schema refuses a registry with a scheme or a path and a repository with a tag, a digest or upper case letters, which Helm rendered into an invalid image reference before.
- **A stalled `APPLYING` is offered again.** When an agent reports `APPLYING` for the desired configuration on a connection and the status stays unchanged for `opamp.staleApplyingAfter` (new setting, default 90 seconds), `myriarchd` offers the configuration once more on that connection, once per connection and never for a hash marked failed. The agent event `config_offered` carries the reason `stale_applying`. Before, a target in this state waited until the `applyTimeout` of its rollout policy, 10 minutes for configuration by default; a supervisor that restarts while it applies reports the stored `APPLYING` again and nothing ends it. A supervisor answers the repeated offer of an unchanged configuration with `APPLIED` and does not restart the collector. What to do: nothing. To keep the old behaviour set `opamp.staleApplyingAfter: 0`; keep a value above the `config_apply_timeout` of your supervisors (30 seconds in the shipped templates), so that a supervisor that is only slow is not offered the configuration again. A negative value is refused at startup.
- **The warning `bridge_selected` can fail a strict GitOps check.** `myrctl validate` and the GitOps sync warn when the selector of a fleet also matches an OpAMP Bridge agent of the OpenTelemetry Operator and the fleet does not set the new field `spec.bridge.manage`. An empty selector triggers it, and so does a selector made only of `NotIn` and `DoesNotExist` conditions; so does a sample agent of the repository that is a Bridge and matches such a fleet. A CI that runs `myrctl validate --strict` fails on the warning; without `--strict` the exit code stays 0. What to do: narrow the selector with a positive condition on an attribute that a Bridge does not report, for example `os.type` or `site.type` (`{key: os.type, operator: Exists}` replaces an empty selector that is meant to match every collector), or set `spec.bridge.manage: true` on a fleet that is meant to configure Bridges in standalone mode. Fleets with a positive condition (`matchAttributes`, `In`, `Exists` or `Glob`) on `os.type`, a `site.*` attribute or `labels.*` are not affected. A sample agent that is a Bridge is no longer rendered and does not have to match a fleet.
- **The installers stop at a package of the upstream project.** `install-linux.sh` and `install-windows.ps1` stop with `conflicting_install`, before they change anything, when a package of the upstream project would run a collector next to the one that myriarch manages: on Windows a service `opampsupervisor` (supervisor MSI) or `otelcol-contrib` (contrib MSI), in any state; on Linux the unit `otelcol-contrib.service` or `opampsupervisor.service` of a deb or rpm package, active or enabled. The installers of v0.1.0 went on and left two collectors on the host, and a re-run on a host that was set up next to such a package stops now as well. Nothing is removed. What to do: remove the package as the message and the table "When the installer stops" in [Connect a host](docs/tasks/connect-a-host.md#when-the-installer-stops) describe, and run the installer again. A package whose units neither run nor are enabled (the rpm packages since 0.157.0 start nothing) does not stop the installer.
- **Helm chart: a test Pod, and a source for it in the NetworkPolicy.** The chart renders the Pod of `helm test` (`templates/tests/test-connection.yaml`, the Helm hook `test`, value `tests.enabled`, default `true`). Helm creates it only while `helm test` runs, so an installation or an upgrade creates no Pod. Tools that render hooks as ordinary resources create it as a normal Pod that runs once and ends: `helm template | kubectl apply` does (add `--skip-tests`), and `tests.enabled: false` removes it. With `networkPolicy.ingress.allowSameNamespace: false` and without `config.server.trustedProxies` and `config.opamp.clientCertHeader`, the NetworkPolicy gets one more source for port 8080, a pod selector with the labels of the test Pod (`app.kubernetes.io/component: test`), which every pod of the namespace that carries these labels can use. To keep the policy of v0.1.0, in which no pod of the namespace reaches port 8080 unless `networkPolicy.ingress.from` names it, set `tests.enabled: false`. With `trustedProxies` or `clientCertHeader` set the chart adds no rule, and `helm test` can connect only if `networkPolicy.ingress.from` names the test Pod. The default `allowSameNamespace: true` already admits every pod of the namespace. `helm upgrade --reuse-values` renders the chart with the values of the installed release in place of its own defaults, and the values of v0.1.0 have neither `tests` nor `prometheusRule`: the chart then renders as v0.1.0 did, without the test Pod, without the NetworkPolicy source for it and without the PrometheusRule, and `--set tests.enabled=true` on top of them gives a Pod without requests and limits. To get the defaults of the new chart, upgrade with `--reset-then-reuse-values` or with a values file (`helm get values <release> -n <namespace> -o yaml`). See [Install with Helm](docs/operations/install-helm.md#test-the-installation).
- **`install.grantTtl` must not exceed `artifacts.downloadTokenTtl`.** The new setting `install.grantTtl` (default 1 hour) is the lifetime of the install grants, and production refuses a value above `artifacts.downloadTokenTtl`. A configuration of v0.1.0 that shortened `artifacts.downloadTokenTtl` below one hour and does not know the new setting stays valid: when `install.grantTtl` is left out (in the file and in `MYRIARCH_INSTALL_GRANTTTL`), its default is the shorter of one hour and `artifacts.downloadTokenTtl`. A value that you set yourself is checked as written. Set `install.grantTtl` to at most `artifacts.downloadTokenTtl`, or turn the installation from the server off with `install.enabled: false`, and run `myriarchd config validate` before you update.
- **A server that runs a release fetches the installer bundles of its own release.** From v0.2.0, every replica of a server that runs a release (not a build from a Git checkout) fetches `checksums.txt`, its Sigstore bundle and the updater archives of that release for the platforms of `install.platforms` (three by default) from `install.bundleSourceBaseUrl`, shortly after the start (15 seconds) and again when somebody renders the install commands or asks for a bundle. The default source is the GitHub releases of the project (`github.com/myriarch/myriarch`), so this is a new outbound connection of the server, through `outbound.allowedCidrs`, `artifacts.proxyUrl` and `artifacts.allowedRedirectHosts`. A server that cannot reach the source logs a warning and shows the bundles as `failed`; nothing else is affected, and the commands cannot be rendered until it can. In an air gap, point `install.bundleSourceBaseUrl` to an internal mirror with the layout `<base>/v<version>/<asset>`, or set `install.enabled: false`, which keeps the surface of v0.1.0: the routes answer 404 and nothing is fetched. The bundles take about 25 MB of `artifacts.dir` for each release and replica, outside `artifacts.maxCacheBytes`; the archives of an earlier version are removed after a day. See [Server behaviour](docs/design/opamp-server.md#installer-bundles).
- **Enrollment tokens are install credentials now.** With the default `install.enabled: true`, an enrollment token also authorizes two routes that need no session, `POST /api/v1/install/plan` and `GET /api/v1/install/bundles/{filename}` (also where `opamp.requireEnrollmentToken` is off), and, through the install grants of a plan, the download of collector and supervisor with their checksums and signatures. Its holder can ask for plans for the platforms of `install.platforms` and so make the server prepare every release that the frame of its fleet allows. Handle the tokens as before and treat them as fleet credentials: one token for each channel or region, and revoke one that may have leaked, which stops its grants at once. Set `install.enabled: false` if the hosts of your sites are installed on the manual path only. See [Host installation from the server](docs/security/model.md#host-installation-from-the-server).

### Added

- **Schema compatibility level.** Migration `00006_schema_compat.sql` adds the table `schema_compat` with one row. Its column `min_binary_schema` is the lowest schema level (the highest migration number a binary embeds) that a binary needs to run on the database. It starts at 3 and never exceeds the schema version. From 00006 on, the header of every migration states whether it is expand only (the level stays) or raises the level, a migration that raises it sets the value in Up and restores the previous one in Down, and tests check the statements against the effect ([ADR-0036](docs/adr/0036-database-schema-compatibility-and-rollback.md), [development guide](docs/development.md)).
- **`myriarchd migrate --check`** changes nothing: it prints the schema version, the compatibility level, the schema level of the binary and a status (`current`, `pending`, `newer` or `incompatible`) and tells the state by its exit code: 0 ready, 3 migrations pending, 4 incompatible, 1 error. Without `--check`, an incompatible schema is refused with exit code 4 as well.
- **Helm chart: values schema.** `deploy/helm/myriarch/values.schema.json` (JSON Schema draft 2020-12) validates the values of the chart. Every object that the chart defines is closed, the Kubernetes objects that it passes on (such as volumes, security contexts, affinity terms and Gateway API references) are open, and the block `config` has the keys, types, nesting and descriptions of `internal/config`. A parent chart that includes the chart as a dependency keeps working: `global` and the key `enabled` of the usual `condition: myriarch.enabled` are accepted. `make docs-gen` generates the file from the hand-written `values.schema.source.yaml` and the configuration struct (a new generator in `internal/refdoc`); `ci/check-docs-gen.sh` fails on drift, and the unit tests fail on a value that `values.yaml` or a template uses and the schema lacks and on a setting of the configuration that is named like a secret and can hold text.
- **Helm chart: image reference.** `image.registry` and `global.imageRegistry` (see the upgrade notes). `podDisruptionBudget.maxUnavailable`, which the template already read, is now a documented value.
- **Helm chart: Artifact Hub metadata.** `Chart.yaml` has the icon, the maintainers (the project address), the category, links to the documentation, the sources, the issues and the security policy, `artifacthub.io/operator` and a placeholder for the images that the release job completes with the digest.
- **Stale `APPLYING`.** The setting `opamp.staleApplyingAfter` (default 90 seconds, `0` turns it off), the counter `myriarch_opamp_config_reoffers_total` (label `reason`, value `stale_applying`) and the reason `stale_applying` in the details of the agent event `config_offered`. The rule is described in [Server behaviour](docs/design/opamp-server.md#stale-applying-after-a-reconnect).
- **`spec.bridge.manage`.** The new field of a Fleet (default `false`) opts the fleet in to configure OpAMP Bridge agents. The opt-in applies to Bridges in standalone mode only. The new warning `bridge_selected` names selectors that also match a Bridge. The REST API returns the block as `bridge` of a fleet when it is set. See [Fleets](docs/concepts/fleets.md#bridge-agents) and the [schema reference](docs/reference/gitops-schema.md#fleet).
- **Dependency review.** Pull requests and merge groups run a dependency review (`dependency-review` in `ci.yml`, a member of `ci-ok`): `actions/dependency-review-action` compares the dependency graph with the base and fails when a dependency that the change adds or updates, in the runtime scope, carries a license outside the CNCF allowlist (and Apache-2.0) or has a known advisory of high or critical severity. The review checks what the dependency graph of GitHub reports for the change with the scope runtime; which ecosystems (Go, npm, Python, GitHub Actions) that covers follows the dependency graph and is to be confirmed by the first runs. It holds the read-only token, writes no comment and asks no third party. `ci/license-allowlist.txt` is the source of both license lists: its list `release` is the binding allowlist of `ci/check-release-licenses.sh` for the Go packages of the release builds, which is as strict as before (the npm packages of the embedded web UI are checked against a license list by the review only; `tslib` under 0BSD ships in it today), and all its entries are the `allow-licenses` of `.github/dependency-review-config.yml`; `ci/tests/license-allowlist-test.sh` keeps the two in step and refuses an exception without a reason. The configuration records an exception, with its reason, for each of the 80 packages of the current dependency set that the review would otherwise report (tools, development trees, the brand generator, packages with combined permissive licenses). `pkg:npm/elkjs` (EPL-2.0, a dependency of Mermaid) has none until it is decided whether the website needs a notice for it, so a change that adds it or changes its resolved version fails the review. See [ADR-0038](docs/adr/0038-dependency-license-policy.md) and "Dependency review" in `docs/development.md`.
- **Vulnerability reports in code scanning.** The workflow `vulncheck.yml` (pushes to `main`, daily, by hand) reports `govulncheck` to the code scanning alerts as SARIF: the code of `main` built like a release and with the build tag `devpg` (`ci/vulncheck.sh --sarif DIR`) and the programs of the latest stable release (`ci/vulncheck-binaries.sh`, binary mode over the 16 archives). The scan of the binaries starts only after the keyless signature of `checksums.txt` and the SHA-256 of every archive were verified, and it reads out only the program of each archive. The release binaries are stripped (`-s -w`), and govulncheck cannot read the symbols of a stripped program (at its default level it would report every vulnerable symbol of an affected module as called), so the scan runs at module level: a result is a warning that says that a release was built with a module or Go version that an advisory affects, not that a binary contains or calls the vulnerable code. A finding that only the binary report has is closed by a release with the fixed version or dismissed in code scanning with a reason, not added to the allowlist of the gate. Findings that `ci/vulncheck-allowlist.txt` accepts are left out until the review date of the entry has passed; from the day after, they are reported again, while the gate only warns. A manual run that names a release (`release_tag`) reports its binary scan to its own category, `govulncheck/binaries-manual`, so that it does not replace the analysis of the latest stable release. The workflow blocks nothing (the gate `vulncheck` in `compliance` still does); its only write scope, `security-events: write` in the job `upload`, is listed and reviewed in `ci/workflow-permissions.txt`, and that job runs no code of the repository.
- **Mirror builder.** `scripts/build-mirror-image-crane.sh` mirrors the OpAMP supervisor as well when `COMPONENTS="contrib supervisor"` is set (the default stays `contrib`): `cmd/opampsupervisor/v<version>/opampsupervisor_<version>_<os>_<arch>[.exe]` with its `.sha256` and `.sigstore.json`, in the layout of the upstream releases, each bundle verified offline against the supervisor release workflow (`base-binary-release.yaml`) for exactly that tag. One directory (`OUT_DIR`) therefore serves `artifacts.sourceBaseUrl` of `myriarchd` and `--release-base-url` of the installers. A platform for which upstream publishes no supervisor is skipped with a warning. `VERIFIER_BIN` names a `myriarch-updater` to verify with instead of building one. `ci/tests/image-crane-test.sh` covers the layout, the identities and the failure cases offline.
- **Host end-to-end test.** `scripts/host-e2e/linux.sh manual`, run by `.github/workflows/host-e2e.yml` on fresh Ubuntu 24.04 runner VMs (amd64 and arm64) every night, for pull requests that touch the installer, the updater, the templates of a host or the harness, and on request, installs the collector, the supervisor and the `myriarch-updater` with `install-linux.sh` as root (https, offline Sigstore verification, no `--insecure`) from a mirror of the real upstream release files, against a `myriarchd` built from the commit. It checks the services under systemd, the registration (fleet, `in_sync`, health), a second run of the installer that changes nothing, the refusal of a tampered archive, an update with a killed collector (automatic rollback) and its retry, and `--uninstall --purge` with the proof that nothing is left. The scripts refuse to run unless `CI=true` and `HOST_E2E=1` are set, on Linux, not as root and on a host without an earlier installation; a failed run uploads an allow-list of scrubbed log files, also a run that hangs (the step that runs the scenario has a timeout of its own, below that of the job, so that it counts as failed and the upload runs, and the harness saves the files right after the diagnostics). The harness (`scripts/host-e2e/lib.sh`) is separate from the scenario, so that a further scenario is a function and a step of the workflow. `ci/tests/host-e2e-test.sh` tests the guard, the scrubber, the allow-list, the throwaway CA and the file server without a host. See "Host end-to-end test" in the development guide.
- **Kubernetes probe in CI.** `.github/workflows/e2e-kind.yml` runs the probe of `hack/kind` (`make kind-probe`) on a kind cluster on a runner every night, for pull requests that touch the chart, the updater, the images (their build scripts and pins), the tools or the probe, and on request (`PROBE_SKIP` skips optional parts). The matrix entry names the pin of `hack/kind/versions.env` that holds the node image (`image-var`), so a second Kubernetes version is a pin and an entry. The job summary shows the summary block of the probe, and a failed run uploads an allow-list from `.cache/kind` (log, results, durations, pod logs, diagnostics) and never the kubeconfig, the generated secrets or cookie jars; the step that runs the probe has a timeout of its own, below that of the job, so that a probe that hangs still uploads. Neither workflow is part of `ci-ok`. `ci/tests/workflow-artifacts-test.sh` emulates the glob rules of `actions/upload-artifact` and holds the patterns of both upload steps against names that must and must not be uploaded, the timeouts of the steps that run a test below that of the job, and the path filter of the kind workflow to the files that the probe depends on, with copies of the workflows that are broken on purpose.
- **Website: canonical links, structured data and `llms.txt`.** Every page now names its original: one absolute `<link rel="canonical">` below the production origin `https://myriarch.dev/`, also in previews, which are built with another base URL (`params.seo.canonicalBase`, an origin without a path that is checked against `baseURL`); the 404 page has none. The home page carries structured data in JSON-LD, a `SoftwareSourceCode` (repository, license Apache-2.0, languages, and the `version` of the latest release in `data/release.yaml`) and a `WebSite`, and every page below `/docs/`, `/project/` and `/legal/` carries a `BreadcrumbList` that equals its visible breadcrumb (the three section pages themselves show no breadcrumb, because Docsy hides a trail of one item, and so have no list). The home page has a title that says what the project is (`params.seo.homeTitle`) instead of the bare site title. `/llms.txt` is a curated summary for language models (what the project does and for whom, key terms, the most important pages), written from `data/llms.yaml` by `layouts/home.llms.txt` through the output format `LLMS` of Docsy and announced in every page by a `rel="describedby"` link and a visually hidden line for AI agents. `robots.txt` states the crawler policy in a comment: every crawler may read the site, and the firewall of the host only logs. The 404 page is now `noindex`, because a static host may serve `404.html` under its own address with status 200. The new check `website/scripts/check-seo.py` enforces all of it in the website gate, for the production build and for previews: one canonical link per page that names the page, JSON-LD that parses, uses only properties its type defines and equals the configuration, the release file and the visible breadcrumb, an `llms.txt` of the right shape (every list item below a heading is a link, as llmstxt.org has it) that links only to the site and the repository, a 404 page that cannot be indexed, no blocked crawler in the production `robots.txt`, a sitemap that equals the canonical links, alt text on every image and the spelling rule of ADR-0015 in the home title and `llms.txt`. `check-indexing.py` exempts the 404 page from the production `noindex` rule. `website/README.md` has the section "SEO and GEO" with the runbook for Search Console, Bing and the validators.
- **Preflight checks of the installers.** Three new error codes, listed in the catalog at the top of `install-linux.sh` and in `deploy/windows/README.md`. `language_mode_unsupported` (Windows): the first action of `install-windows.ps1` checks the PowerShell language mode, and in any mode below `FullLanguage` (App Control for Business with script enforcement runs an unsigned script in Constrained Language Mode) the run stops, names the file and the rule that lets it run (a hash rule created from the verified copy) and changes nothing; the installer of v0.1.0 failed on its first method call with "Cannot invoke method. Method invocation is supported only on core types in this language mode". `conflicting_install` (both installers): see the upgrade notes. `supervisor_missing` (both installers): when the installation step of the supervisor is over, the file has to be at the path of the service, an executable file on Linux (`/opt/myriarch/supervisor/opampsupervisor`), a regular file with the SHA-256 that was verified on Windows (`C:\Program Files\Myriarch\supervisor\opampsupervisor.exe`); otherwise the run stops with the path and the next step (the protection history of the antivirus, a `noexec` mount). On Windows the `VERSION` file of the supervisor folder, which lets a re-run take the installed file as it is, is removed before the file is replaced and written only after the check, so a run that stopped at the check fetches and verifies the file again. A directory or a link at the path is not replaced: the message tells to remove it, because a new run would stop at the same item (on Windows the run stops before it downloads anything). A security tool that quarantines the unsigned binary no longer shows up only as a service that does not start.
- **Remaining health wait on the rollout page.** A target that has reported success waits in `verifying` for the `healthWait` of its policy, 5 minutes in the example version policy, and the page did not say how long was left or why. It now shows the time that is left in the status column of the target list, in the step *Health wait* of the progress of a version target and on the card of a wave (the number of its targets in the health wait and the end of the one that finishes last). At 0 it says "finishing…" until the engine has evaluated the target. It keeps counting while the rollout is paused, because the engine keeps evaluating running targets, and it disappears when the target reaches a final status; it shows nothing for a rollout that the engine does not evaluate (`failed`, `rolling_back` and the final statuses). The step and the wave card also name the source of the wait: `Policy <name> · healthWait <duration> · <path>@<commit>`, with a link to the policy, where path and commit are those of the policy snapshot of the rollout. The API gets no new field: the browser computes the end as `verifiedAt` plus `policy.healthWait` (60 seconds when the snapshot has none), the rule of the engine, from what `GET /rollouts/{id}` and `GET /rollouts/{id}/targets` already return, and counts down with its own clock. The rule is in [Rollouts](docs/concepts/rollouts.md#health-wait) and in [Server behaviour](docs/design/opamp-server.md#targets).
- **`myriarchd healthcheck`.** A command that checks a running server and tells the result by its exit code. It asks `GET /readyz` (200) and then for a WebSocket upgrade at the OpAMP path: without a token the server must refuse it with 401 (route and authentication are in place), with `--token-file` it must accept it with 101; the command then closes the connection in the normal way. It sends no OpAMP message, so it registers no agent and stores nothing. Flags: `--url` (default `http://127.0.0.1:8080`), `--opamp-path`, `--token-file`, `--ca-file` and `--timeout` (default `10s`). Exit codes: 0 healthy, 1 not healthy, 2 wrong usage, 3 no answer. It is the health check of the container image, which has neither a shell nor curl (`["CMD", "/usr/local/bin/myriarchd", "healthcheck"]`), and the program of the Pod of `helm test`. See [Server behaviour](docs/design/opamp-server.md#health-check) and the [command reference](docs/reference/cli/myriarchd_healthcheck.md).
- **Helm chart: `helm test`.** The Pod of the test runs `myriarchd healthcheck` of the server image against the Service of the release under the restricted Pod Security profile (no user ID in the OpenShift profile, no service account token, no Secret and no environment variable). It expects the 401 for the OpAMP upgrade without a token; with `tests.token.existingSecret` and `tests.token.key` (opt-in, a Secret with an enrollment token that exists for the test only) it expects the upgrade (101). `tests.resources` sets the requests and limits, and `tests.podAnnotations` adds annotations (for example the opt-out from the sidecar injection of a service mesh; the chart sets the annotations of the hook itself, so a key that starts with `helm.sh/hook` is refused). The README of the chart describes the test, the NetworkPolicy rule and the opt-in.
- **Helm chart: PrometheusRule.** `prometheusRule.enabled` (default `false`) renders a PrometheusRule with the 13 alerts of `deploy/examples/production/monitoring/prometheusrule.yaml` (no leader, more than one leader, replicas not ready, metrics unreachable, dropped and rejected OpAMP connections, unauthorized connects, release tracker, GitOps sync, rollouts, notifications and housekeeping); `prometheusRule.labels` adds labels, for example the one that selects the rule in the Prometheus resource. The rules select the metrics by the name of the Service (the `job` of the ServiceMonitor of the chart) and the namespace of the release, and the replica alert compares with `replicaCount`. The example for clusters without Helm has the same rules with the namespace matcher added, and `ci/helm-conform.sh` fails when the two differ. There is no dashboard.
- **Install plan.** `POST /api/v1/install/plan` (operation `getInstallPlan`, new tag `install`) gives a host that is not enrolled yet its plan: the fleet it would join, the version of collector and supervisor, the OpAMP endpoint, the URLs of the artifacts on the server with an install grant for each, and whether the updater is installed ([ADR-0046](docs/adr/0046-host-installation-from-the-server.md)). The host presents the enrollment token that it will use, always, also where `opamp.requireEnrollmentToken` is off. The server decides the fleet with the function that assigns a connected agent (the reported site attributes and the labels of the token); a fleet named in the request that disagrees is 409. The version is the effective target of the fleet; while a version rollout of the fleet is pending, running or waiting for approval it is the version before that rollout, so that the new host becomes a straggler of the last wave; a paused, failed or rolling back rollout is 409 `rollout_blocking`, a fleet on hold or without a target 412 `no_target_version`, and a version that the host asks for is accepted inside the frame in Git only (422). The release tracker must know both releases. Until the collector and the supervisor for the platform are downloaded the answer is 503 `preparing` with `Retry-After` (the first request for a platform downloads about 112 MB). The plan is `text/plain` (one `key=value` line each, values from `A-Z a-z 0-9 . _ : / @ + = -`, at most 64 lines and 8 KiB, so that bash without `jq` and PowerShell 5.1 can read it) or JSON with `Accept: application/json`; a refusal is a problem document whose first issue carries the reason. The route is off with `install.enabled: false`. Nothing in the installers of v0.1.0 uses it. See [Server behaviour](docs/design/opamp-server.md#installation-from-the-server) and the [API reference](docs/reference/api/install.md).
- **Install plan.** `POST /api/v1/install/plan` (operation `getInstallPlan`, new tag `install`) gives a host that is not enrolled yet its plan: the fleet it would join, the version of collector and supervisor, the OpAMP endpoint, the URLs of the artifacts on the server with an install grant for each, and whether the updater is installed ([ADR-0046](docs/adr/0046-host-installation-from-the-server.md)). The host presents the enrollment token that it will use, always, also where `opamp.requireEnrollmentToken` is off. The server decides the fleet with the function that assigns a connected agent (the reported site attributes and the labels of the token); a fleet named in the request that disagrees is 409. The version is the effective target of the fleet; while a version rollout of the fleet is pending, running or waiting for approval it is the version before that rollout, so that the new host becomes a straggler of the last wave; a paused, failed or rolling back rollout is 409 `rollout_blocking`, a fleet on hold or without a target 412 `no_target_version`, and a version that the host asks for is accepted inside the frame in Git only (422). A target that the leader has not planned yet (a new target in Git, a new selection in the UI) is not handed out: the answer is 503 `preparing` with `Retry-After` until the rollout planner has created the rollout, so that a new host cannot skip the waves and approvals in the time between the change and the rollout. The release tracker must know both releases. Until the collector and the supervisor for the platform are downloaded the answer is 503 `preparing` with `Retry-After` (the first request for a platform downloads about 112 MB). The plan is `text/plain` (one `key=value` line each, values from `A-Z a-z 0-9 . _ : / @ + = -`, at most 64 lines and 8 KiB, so that bash without `jq` and PowerShell 5.1 can read it) or JSON with `Accept: application/json`; a refusal is a problem document whose first issue carries the reason. The route is off with `install.enabled: false`. Nothing in the installers of v0.1.0 uses it. See [Server behaviour](docs/design/opamp-server.md#installation-from-the-server) and the [API reference](docs/reference/api/install.md).
- **Install grants.** A second kind of `myrd_` download token for hosts that have no agent ID and no package offer yet. A grant is bound to one artifact and to the enrollment token of the request for the plan, and serves the artifact, its `.sha256` and its `.sigstore.json` (the files an installer checks it with) until `install.grantTtl` has passed, and only while that enrollment token is valid: revoking the token stops its grants at once on every replica. Turning the installation off (`install.enabled: false`) stops them too: a server that restarts with the setting off refuses the grants that it gave before. The token of a package offer and an install grant cannot be used for each other, and the token of an offer is unchanged.
- **Install settings and metric.** The section `install` of the configuration has `install.enabled` (default `true`), `install.grantTtl` (default 1 hour, or `artifacts.downloadTokenTtl` when that is shorter and the setting is left out; production: positive and at most `artifacts.downloadTokenTtl`), `install.bundleSourceBaseUrl` (the release source of the installer bundles of the server's own release, default the GitHub releases of the project, never empty, production: https) and `install.platforms` (`linux/amd64`, `linux/arm64`, `windows/amd64`). The server warns at start when `install.enabled` is on and `releases.enabled` is off. The counter `myriarch_install_plans_total{result}` counts the plan requests.
- **Installer bundles.** The server keeps the updater archive of the release that it runs for each platform of `install.platforms` (`myriarch-updater_<version>_<os>_<arch>.tar.gz` or `.zip`: the installer scripts, their templates and the `myriarch-updater` binary) and delivers it to hosts with `GET /api/v1/install/bundles/{filename}` (`downloadInstallBundle`), after the authentication of the plan: an enrollment token, always, the same 401 for every problem of a token, 429 for too many failures. The list is `GET /api/v1/install/bundles` (`listInstallBundles`, permission `read`). Before it fetches an archive from `install.bundleSourceBaseUrl`, the server verifies the keyless signature of `checksums.txt` of its own release against the release workflow of this project at the tag of its version (derived from the code, issuer GitHub Actions, the trusted root of `artifacts.verify`) and requires exactly one line for the archive that the archive matches. The archive is stored under its SHA-256, hashed again before every delivery and sent from the same open file; an archive that changed on the disk is fetched again. The bytes of the release are never templated or repacked, which keeps App Control hash rules and later Authenticode signatures valid. Only a release has bundles (`MAJOR.MINOR.PATCH` or `-rc.N`, from 0.2.0); a build from a Git checkout has none. The source is fetched like every outbound connection (destination policy, `artifacts.proxyUrl`, redirect rules, size limits) and without credentials, by every replica for itself. The counter `myriarch_install_bundle_downloads_total{result}` counts the downloads. See [Server behaviour](docs/design/opamp-server.md#installer-bundles) and the [security model](docs/security/model.md#host-installation-from-the-server).
- **Install commands.** `POST /api/v1/install/commands` (`renderInstallCommands`, permission `read`, the CSRF header for a cookie session) renders, for each platform, the command that a person copies to a host: it downloads the installer bundle, checks the SHA-256 that it pins before it unpacks anything, and starts the installer from the bundle. The server never sees a token: the variant `token_inline` has a placeholder (`@@MYRIARCH_ENROLLMENT_TOKEN@@`) that the web UI replaces in the browser, the variant `token_file` reads the token from a file on the host. On Linux the token goes through the standard input of a root shell and is read and written by builtins, reaches `curl` as a header through `curl -K -`, lives in a private `mktemp -d` directory of root and is deleted with it; on Windows the working directory below `%ProgramData%` is restricted to SYSTEM and the administrators before the first download, the installer starts with `-ExecutionPolicy RemoteSigned` for that process only (never `Bypass`), and the script uses cmdlets and native programs only, so it runs in Constrained Language Mode. It runs in an elevated Windows PowerShell (integrity level High) and in a session of SYSTEM (level System), the context of scheduled tasks and management agents. The text of a command is a constant; every value is a quoted argument of its own, checked against an allowlist first (no quotation mark of any kind including U+2018 to U+201E, no backtick, `$`, `;` or control character, nothing that looks like a token), and anything else is 422. A command that carries a token needs an https server, and a server with `opamp.requireClientCert` renders none (412 `server_settings`) because the command cannot present a client certificate: such hosts use the manual path. A command starts the installer in the bundle with the options `--server` and `--fleet` (`-Server`, `-Fleet`) of its server mode, which the installers of v0.1.0 do not have: it works with the installers of the same release, which take versions and artifacts from the plan. See [Server behaviour](docs/design/opamp-server.md#install-commands).
- **`myriarchd dev --install-bundle-dir`.** A development server can serve the installer bundles from a directory of archives that are named like the ones of a release. The archives carry no signature, so only `dev` has the flag; `serve` refuses it with a message that says why, and the start refuses a directory outside development mode.

### Changed

- **Website.** The search index loads when a visitor first uses a search box, not on every page load. Docsy's script fetched the index (about 1.2 MB of JSON, 375 KB compressed) and built the lunr index at `DOMContentLoaded`; that one long task, about 0.5 s on a phone, was the whole Total Blocking Time of the landing page (440 to 490 ms, performance 72 on mobile and 80 on desktop in PageSpeed Insights). A page now requests the index when a search box first receives the focus, a pointer press or an input, once for all boxes on the page, and renders a query that is submitted before the index has arrived as soon as it has; the results are the same. A load that fails (the network is down for a moment, or the tab was opened before a deployment and names an index file that the host no longer serves) is logged and tried again with the next query, and a query that waited for it gets a hint in its popover that asks for a reload. In a Lighthouse lab run with the throttling applied to the browser, the Total Blocking Time of the landing page on the mobile profile falls from about 400 ms to 0 ms and the performance score rises from 89 to 98. The script is an override of `assets/js/offline-search.js` of Docsy 0.18.0, pinned in `website/overrides.txt`; `check-overrides.py` now also covers the files of `website/assets` that replace a theme file, and `check-requests.mjs` fails when a page requests the index while it loads, when the search requests it other than once or when it does not recover from an index that fails to load.
- **Start and migrations.** `myriarchd serve`, `myriarchd dev` and `myriarchd migrate` share one schema step. An incompatible schema is refused before anything is changed, a newer schema within the compatibility level starts with a warning, and the log line `database schema ready` names the schema version, the compatibility level and the schema level. The generated references (configuration, environment variables, CLI) state that `migrate` loads the database settings only.
- **Tool installation.** `ci/install-tools.sh` retries a download after a transient failure instead of failing the job: a release download (kubectl, shellcheck, `pwsh`, Hugo, Dart Sass, lychee, syft, zizmor, the source of osslsigncode) after a timeout, a failed connection or HTTP 408, 429, 500, 502, 503 or 504, with pauses of 1, 2, 4, ... s and no attempt later than 120 s after the first (the policy of the installers), and a Go tool (kind, helm and the others) up to four times, 5, 10 and 20 s apart, when `go build` fails with a network error of the module download. A 404, a certificate error, a checksum that differs from the pin, a failed module verification and a compiler error still end the script at once, and the checks after a download are unchanged. `smoke-kind` of the release workflow benefits; `docs/releasing.md` and `ci/release/smoke.sh` say which steps still have a shorter policy of their own.
- **Windows installer: ARM64 stops before anything is changed.** Without `-Arch amd64` the installer stops with `unsupported_platform` as soon as it knows the architecture, before the work directory, the downloads, the verifier and the stop of the service. The installer of v0.1.0 stopped only at the supervisor step, after it had stopped the service and installed the ARM64 collector, which the next run kept.
- **Windows installer: a service that does not start is explained by its file.** When `otelcol-supervisor` is not running at the end of the run, the installer first checks the file of the binPath that the service has in the registry. A file that is gone is reported as `supervisor_missing`, with the path, in place of `service_not_running`; otherwise `service_not_running` is as before. At the top of the script, the error line is printed with `Write-Host` in a restricted language mode, where a method call on the host is refused.
- **The rollout planner records the target it handled.** After it planned a fleet without an error, the planner writes the effective target version of the fleet to the key-value store (`rollout/planned-target/<fleet>`, when it changes and after it created the rollout; empty for a fleet without a target), next to `plannedAt` of a selection. The installation of hosts from the server reads it on every replica and waits until it equals the target ([Planner](docs/design/opamp-server.md#planner)). There is no setting and no migration; a leader writes the records again when it starts a term.

### Fixed

- **Install examples in the enrollment-token dialog.** The Linux and Windows examples left out inputs that both installers require: without `--collector-version` (`-CollectorVersion`) they stop with `option_missing`, and without a Sigstore verifier with `sigstore_verifier_missing`. They also started the script next to nothing, although it reads its templates from the directory above its own and has to run from the unpacked updater archive, and the Windows example started `install-windows.ps1` directly, which the default execution policy `Restricted` refuses. The examples now run `deploy/scripts/install-linux.sh` and `deploy\scripts\install-windows.ps1` from that archive, name the collector version and the verifier (`--verifier`, `-Verifier`), and start the Windows installer with `powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File ...`, which sets the execution policy for that one process and changes no setting of the machine. The Linux example runs in a root shell, in a directory that only root can write, without `sudo`, and takes the verifier as a full path (`cosign`, or the `myriarch-updater` of the archive), because a directory or a `cosign` that the invoking user can write lets that user change what root runs. The token still reaches the installer only through a file that a shell builtin or `Set-Content` writes and the example deletes, and it appears in no other line. The Windows example gives that file its own DACL for SYSTEM and the administrators before the token is written, because a folder below `C:\Program Files` that only administrators can write can still be read by every local user. Both examples say in a comment that the pasted command, token included, is recorded by a shell history, a PowerShell transcript or script block log and a terminal recording. `internal/updater/deploy_snippets_test.go` reads the required options from the installers and fails when the examples do not name them.
- **Configuration targets no longer wait for the `applyTimeout` after a restart in the middle of applying.** An agent that restarted while it applied a configuration reported the stored `APPLYING` for the desired hash after it reconnected, and the server never offered a hash again that the agent reported as `APPLYING`; the rollout target stayed in progress until its `applyTimeout`. The server now offers the configuration once more after `opamp.staleApplyingAfter` (see the upgrade notes). The documentation of the supervisor behaviour is in [Upstream notes](docs/design/upstream-notes.md#restart-while-a-remote-config-is-applying).
- **Updates of Linux hosts stopped in the preflight.** The systemd unit `myriarch-updater.service` set `NoNewPrivileges=true`, and with it the updater could not start the new collector under the account of the supervisor for the preflight (`otelcol-contrib validate`): every update through the updater failed in the step `verifying` with "operation not permitted", and the old version kept running. The unit no longer sets it. Hosts that were installed with v0.1.0 get the new unit when the installer of this release runs again; until then a drop-in with `NoNewPrivileges=false` helps ([Troubleshooting](docs/operations/troubleshooting.md)). The host end-to-end test found the defect.
- **Usage examples in the headers of the installation scripts.** The example in `install-linux.sh` put the token on the command line and started the script with `sudo` from the current directory, the examples of `install-windows.ps1` and `Set-ServiceEnvironment.ps1` named a file below `C:\Temp`, which unprivileged accounts can write, and started the script directly, which the default execution policy refuses. They now show what [Connect a host](docs/tasks/connect-a-host.md) documents: a root shell and the script from the verified archive, the token in a file that is deleted afterwards, a verifier, and on Windows `Unblock-File` after the checks and `powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File ...` with a file in the setup folder that only SYSTEM and the administrators can read. Tests keep the examples in step with the scripts.

### Security

- **Helm chart: secrets and the development mode are not values.** The values schema offers no key for a database DSN, an OIDC client secret, a webhook secret, the URL of a notification channel or an enrollment token, refuses a Secret reference that has the form of an enrollment token, and offers neither `config.dev` nor `config.auth.devLogin`; the templates keep their own refusals for a run with `--skip-schema-validation`. A test fails for a new setting of the configuration that can hold text (a string, a list of strings or a map of strings) and names a token, secret, password, key, credential, passphrase, bearer token or DSN, unless it holds a file, a directory or a prefix. The controls and their residual risk (free-text values such as annotations or `extraEnv[].value` are not recognized as secrets) are in the section "Helm chart values" of the [security model](docs/security/model.md#helm-chart-values).
- **Helm chart: the switches of the TLS checks are booleans.** `ingress.allowWithoutTls` and `httpRoute.tlsTerminatedAtGateway` must be booleans, and `openshift.route.tls.insecureEdgeTerminationPolicy` one of `Redirect`, `Allow` and `None`. A template counts the string `"false"` as true, so with the templates alone `ingress.allowWithoutTls: "false"` switched the TLS check of the Ingress off; the schema refuses it. The external entry points keep using TLS unless you opt out: the server refuses a `server.publicUrl` that is not https in production, an Ingress needs `ingress.tls` and an HTTPRoute `httpRoute.tlsTerminatedAtGateway` for it, the install notes print `wss://`, and the OpenShift Route redirects plain HTTP unless the policy is `Allow`, the explicit opt-in for plain HTTP and `ws://` at the router. Port 8080 inside the cluster is plain HTTP, limited by the NetworkPolicy; see the residual risk in the [security model](docs/security/model.md#helm-chart-values).
- **Unpinned package manager install removed.** `ci/test-web.sh` had no caller and was the only place that installed pnpm with `npm install --global` without a hash, the open Pinned-Dependencies finding of the OpenSSF Scorecard. The script and the comment that mentioned it are gone. The `web` gate and the CI jobs take pnpm from corepack, at the version of the `packageManager` field of `web/package.json`.
- **`myriarch-updater.service` without `NoNewPrivileges`.** The preflight needs to switch to the account of the supervisor. The rest of the sandbox stays (capability bounding set, `ProtectSystem=strict`, `RestrictSUIDSGID`, restricted namespaces and kernel interfaces); the residual risk is in the [security model](docs/security/model.md).
- **Installers: preflight checks that fail closed.** A host that is not fit for the installation is refused before anything is downloaded, stopped or written, and nothing is removed: a language mode below `FullLanguage` on Windows (the check and its error line work in Constrained Language Mode), the services and units of the packages of the upstream project, and Windows on ARM64 without `-Arch amd64`. After the supervisor step the installers check that the supervisor is a regular file at the path of the service, and on Windows the marker that lets a re-run skip that step is written after the check, so a changed file is not accepted on the next run. The controls and their limits (the check knows two service names and two unit names; the check of the file sees one moment) are in "Preflight checks of the installers" in the [security model](docs/security/model.md).
- **Health check.** `myriarchd healthcheck` reads the enrollment token from a file only, never from an argument, the environment or standard input, and never prints it; the file must be a regular file of at most 4 KiB with one enrollment token, so a file with another secret (the database DSN, the token of the bootstrap admin) is refused before a request is made. The token goes to the host of `--url` only: no redirect is followed, no proxy is used and the certificate of an `https` server is always verified (`--ca-file` narrows the trust to the CAs of that file; a wrong CA fails the check). The command sends no OpAMP message. A check without a token counts as an unauthorized OpAMP connect in `myriarch_opamp_connect_rejected_total` and `myriarch_auth_agent_requests_total`. See [Server behaviour](docs/design/opamp-server.md#health-check).
- **Helm chart: the test Pod.** The Pod of `helm test` follows the restricted Pod Security profile, mounts no Secret and has no environment variable without the opt-in, and its container settings are fixed; the chart refuses the Secrets of the server itself as the test token, and the command refuses a file that holds anything but an enrollment token. Its NetworkPolicy source (with `allowSameNamespace: false`) can be used by every pod that carries the labels of the test Pod, so it never exists together with `trustedProxies` or `clientCertHeader`. The controls and their residual risk are in the section "Health check and Helm test" of the [security model](docs/security/model.md#health-check-and-helm-test).
- **The routes of the installation always need an enrollment token, and their failures are limited.** The plan (and with it the grants) is authenticated by the enrollment token also where `opamp.requireEnrollmentToken` is off, with the lookups and the client certificate rule of the OpAMP endpoint. A missing, malformed, unknown, revoked or expired token gets the same 401, so a request cannot tell whether a token exists. The routes can be reached by anyone and share the bound on token lookups with the OpAMP endpoint, so failed authentications are also limited per client address (30 free, then one per second, IPv6 per /64): an address without budget is answered with 429 before any lookup, and one address cannot use up the lookups that enrolling agents need. The token is read from one header and never written to a log, a metric label, an audit entry, a URL or an answer. See [Host installation from the server](docs/security/model.md#host-installation-from-the-server).
- **The command that installs a host keeps the token out of arguments, URLs and logs.** See the bullet "Install commands" above: the token is read and written by builtins, sent as a header only, kept in a private directory and deleted with it, and the command checks the pinned SHA-256 before it unpacks or runs anything. What typed text leaves behind (shell histories, PSReadLine, PowerShell transcription and script block logging, session recordings) is outside these controls; hosts that record their input use the variant with the token from a file. The first installation trusts the server that displays the command (trust on first use); the [security model](docs/security/model.md#host-installation-from-the-server) lists the residual risks, and the manual path stays for sites that cannot accept them.

### Security

Fixes and hardening from the pre-publication security audit. The controls are described in `docs/security/model.md`; the limitations that remain are in its section "Known limitations".

- **GitOps source.** The clone always follows `gitops.repoUrl`: a changed URL with the same `gitops.cloneDir` no longer keeps applying the previous repository, and an existing clone whose origin differs is replaced.
- **HTTP listeners.** Every request has 60 seconds to deliver its body and an idle write timeout of 60 seconds (accepted event streams and handed-over WebSocket connections are exempt; a rejected request keeps both budgets), request headers are limited to 64 KiB on both listeners, `/readyz` caches the database check for 2 seconds and coalesces concurrent checks, and public state-changing routes (sign-in) require `Content-Type: application/json`.
- **Agent authentication.** The OpAMP connect limit uses one bucket per IPv6 /64 (IPv4-mapped addresses count as IPv4). Only well-formed enrollment tokens are looked up; unknown tokens are cached in a separate small cache, concurrent lookups are coalesced and lookups of uncached tokens are limited per replica (`429` with `Retry-After`). Token usage is written with one statement per token and flush.
- **Sign-in.** Failed OIDC callbacks are limited per client address (both OIDC endpoints refuse an address with an empty bucket), failures before a verified login state are audited at most once per minute and address, and responses of the identity provider are limited to 1 MiB. Group names are matched exactly (no case or Unicode folding) and e-mail entries ignoring the case of ASCII letters only: a mapping that relied on a different case of a group name has to use the exact name. The session cookie is named `__Host-myriarch_session` where cookies are Secure (production); existing sessions end with the upgrade. API tokens of local development accounts are refused where the development login is off.
- **API tokens.** New setting `auth.apiTokenMaxTtl` (default 90 days; `0` means unlimited and logs a warning): a token created without `expiresAt` gets the maximum, a later `expiresAt` is refused with `422`, and older tokens stop working. Existing tokens without an expiry stop working 90 days after their creation. The token list and the web UI show the effective expiry. Offboarding a user at the identity provider does not end API tokens: disable the user in myriarch.
- **Configuration checks.** Production refuses `server.trustedProxies` ranges that cover every address and a zero `artifacts.downloadTokenTtl`, and refuses unanchored `artifacts.verify.certificateIdentityRegexp` patterns. It warns about `/metrics` on the main listener, a remote database connection without certificate verification, empty `artifacts.dir` and `gitops.cloneDir`, secrets set as literal values in the configuration file, credentials in `artifacts.proxyUrl` and very broad trusted proxy ranges. `myriarchd config print` redacts credentials in URL-valued settings. The development mode guard also covers `server.metricsListenAddr`. The removed constant `config.DefaultDataDir` was unused.
- **Outbound policy.** Only the exact proxy address is exempt from the address check and only in the transport that uses it (`ALL_PROXY` exempts nothing), more special-purpose ranges are blocked (IPv4-compatible IPv6, Teredo, the discard prefix, `192.88.99.0/24` and the IPv4 documentation ranges; `outbound.allowedCidrs` can open them), and address literals and `localhost` in a request URL are refused locally when a forward proxy applies.
- **Secret files.** The start-up check also covers files below `executors.secretDir` that are bound in `executors.secretFileHosts` and the directory itself, and operator-chosen executor secret files are read as regular files of at most 1 MiB. `myriarch-updater` warns about loose modes of its token file.
- **Error responses.** Database errors that become 4xx answers no longer carry the operation name, constraint names or driver text; they are logged with the request ID.
- **Installers and units.** The certificate identities passed to `cosign` and `verify-bundle` are bound to the requested version. The Linux installer requires `curl` unless `--insecure` is given, extracts archives without owner and mode, and copies `--ca-file` to `/etc/myriarch/ca.pem` (the configuration files now reference that path; the option takes an absolute path). The Windows installer prefers the verified updater over `cosign.exe` from `PATH`, creates its work directory with a protected DACL, hashes verified files again after copying, and applies and verifies a fresh ACL on the service key before it writes the token (`Set-ServiceEnvironment.ps1` does the same). `otelcol-supervisor.service` drops all capabilities and sets further hardening directives. Both updater and `verify-bundle` refuse unanchored identity patterns.
- **Installers verify the keyless release bundle (breaking).** `--signing-key`, `--updater-checksums-sig-url`, `-SigningKey` and `-UpdaterChecksumsSigUrl` and the key-signed `checksums.txt.sig` were removed; using one fails with `option_removed`, and the message names the replacement (`--updater-checksums-url` with its bundle, `--updater-bundle-url`). The error codes `signature_invalid`, `signature_malformed`, `signature_verifier_missing` and `signing_key_invalid` no longer exist. The verifier of `checksums.txt` is `cosign` 3.0.4 or newer or an already installed `myriarch-updater`, and never the updater that is being installed; an older `cosign` stops the installation with `sigstore_verifier_outdated`, also for the collector and supervisor bundles. `--updater-checksums-url` cannot be combined with `--verify-signatures skip`. A `-Verifier` of the Windows installer must be in a directory that only administrators can write (`directory_unsafe` otherwise), a pre-release of `cosign` 3.0.4 counts as older, and on Linux every `--verifier` whose file name starts with `cosign` gets the version check. `-UpdaterSignerThumbprint` stays for private PKIs (a pinned thumbprint breaks at every certificate renewal). Known limitation: under App Control script enforcement the unsigned `install-windows.ps1` runs in Constrained Language Mode and fails; allow it by its hash.
- **Kubernetes.** The collector manifests set `automountServiceAccountToken: false`, the node agent changes only the top storage directory, and the Helm chart refuses to render inline secrets (`config.database.dsn`, `config.auth.oidc.clientSecret`, `config.gitops.webhookSecret`, `config.notifications.channels[].url`). The examples use `sslmode=verify-full`.
- **Dependencies and gates.** Go 1.27.2 and `golang.org/x/net` 0.60.0 fix the reachable vulnerabilities reported by `govulncheck`. New gates `vulncheck` (with an allowlist that records reason and review date) and `secrets` (gitleaks, `.gitleaks.toml`) in `make check-local`; the `go` gate also vets for Windows and compiles the updater tests for it. The security tests of the updater now compile for Windows.
- **Build and release.** The collector image defaults to the reviewed upstream digests and verifies the upstream binaries by default when it pushes, the `dev` image variant is refused for `ghcr.io/myriarch/*`, and the Docker build contexts exclude every git-ignored path.
- **Verification before publication.** `ci/release/verify.sh` checks the files from which the draft release is created before anyone can publish it: the 42 files, the keyless signature of `checksums.txt` against the exact identity (tag, commit, workflow, trigger), the ADR-0029 pattern and the version-bound pattern of the installers, the build provenance of all 39 listed files, and for both images the index, the platform manifests and configs (user 65532, one layer, labels), the signatures (a cosign signature of the digest, not only an attestation of the same identity), the provenance and SBOM attestations and the tag list. `ci/release/finalize.sh` binds the draft to that result through GitHub's SHA-256 asset digests, refuses unless both packages are readable without credentials and the tag still points at the tagged commit (`tag_moved`), plans all image tags before it sets one (an immutable tag is never moved, `latest` never exists), reads the draft by ID again and repeats the checks directly before it publishes, compares the published, immutable release with the verified files once more (`release_assets_changed`), and checks that the release carries GitHub's release attestation.

### Build

- **Release images.** `ghcr.io/myriarch/myriarch` (`myriarchd`, `myrctl`, `myriarch-sim` and the example repositories) and `ghcr.io/myriarch/myriarch-updater` are image indexes for `linux/amd64` and `linux/arm64`, built `FROM scratch` with one layer from the linux archives of the release build instead of from a second compilation. They run as user and group 65532, hold the license files under `/usr/share/licenses/myriarch/` and carry the OCI labels in the platform configs and the index annotations. `IMAGE_SOURCE=dist IMAGE_KIND=server|updater scripts/build-image-crane.sh` writes a deterministic OCI layout (the same archives give the same uncompressed layers, and the same digests with the same zlib) and one SPDX SBOM per platform; `ci/release/push-images.sh` pushes a layout by digest, never sets a tag and verifies the digest it pushed. See `deploy/README.md`.
- **Server image content and data directory.** The published server image carries `myriarchd` (entrypoint), `myrctl` and `myriarch-sim` in `/usr/local/bin` and the example repositories `/opt/myriarch/examples/quickstart` and `/opt/myriarch/examples/sim`, so a Compose quickstart or a first try needs no repository checkout. All of it is read from the release archives and covered by `checksums.txt`: the `myriarchd` archive now also holds `examples/quickstart`, the builder takes `myrctl` and `myriarch-sim` from their own archives, and it refuses archives whose license files differ. The image creates the empty data directory `/var/lib/myriarchd` (0750, owned by 65532:65532), so a named volume, an `emptyDir` or a PVC mounted there works for the non-root user and the artifact cache survives restarts. `deploy/docker/myriarchd.Dockerfile` and the image built from source follow the same contract, and the development Compose file mounts a named volume at that path. The updater image needs no state directory (container mode keeps it on the volume of the collector image).
- **Image user.** The image that `scripts/build-image-crane.sh` builds from the work tree runs as user and group 65532 (it was 1001), like the Helm chart. It refuses `ghcr.io/myriarch/*`: those repositories are written only by the release workflow.
- **Updater trust store.** `myriarch-updater` embeds the Mozilla root CAs as a fallback, like the other binaries, so that the scratch-based updater image can verify TLS servers. The host trust store still wins.
- **Removed images.** `deploy/docker/myriarchd-release.Dockerfile` and `deploy/docker/myrctl.Dockerfile` are gone, together with `MYRCTL_BASE_IMAGE`. The project publishes no `myrctl` image; the binary is in the release archives, and the GitLab starter in `gitops-template/` says to build an image from it.
- **Collector image.** `deploy/k8s/collector/Dockerfile` can copy `myriarch-updater` from the published updater image (`--build-arg UPDATER_SOURCE=image --build-arg UPDATER_IMAGE=ghcr.io/myriarch/myriarch-updater@sha256:<digest>`). Container mode is beta and needs a self-built collector image until the collector chart of v0.2.0 (`docs/design/container-mode.md`, `ROADMAP.md`).
- **No signing key in the release build.** goreleaser signs nothing (no `signs:` block), `ci/build-release.sh` has only the `snapshot` mode, and `deploy/release/authenticode.sh` is gone. Releases are signed keyless by the release workflow ([ADR-0023](docs/adr/0023-keyless-release-signing.md)). The format contract of key-based signatures and the key handling moved to `contrib/enterprise-mirror/signing.md` for organizations that mirror and re-sign releases.
- **SBOMs.** The release build writes an SPDX JSON SBOM per archive (`<archive>.sbom.json`) and one for the web UI (`myriarch-webui_<version>.sbom.json`, production dependencies only), made with the pinned syft without network access (syft's temporary extraction directory is not listed). `checksums.txt` lists them, and also `LICENSE` and `THIRD_PARTY_NOTICES` (39 entries for a release).
- **Windows version resources.** `myriarch-updater.exe` and `myrctl.exe` carry version information (product "Myriarch", file and product version from the tag, original file name), generated with the pinned go-winres.
- **Windows signing hook.** The release build prepares Authenticode for the Windows files in stages (`MYRIARCH_WINDOWS_STAGE`): the unsigned files are collected, `ci/release/windows-sign-hook.sh` is the contract with a signing provider, and the packaging step accepts a signed file only if its signature, attached to the job's own reproducible build, verifies against the committed chain, subject and RFC 3161 timestamp. A release build has to know the configured signing mode (`MYRIARCH_WINDOWS_SIGNING`) and refuses a hook result of another provider. `make release-rehearsal` walks the whole path in a snapshot with a throwaway test CA, and CI runs it. osslsigncode is built from a pinned source archive (`ci/install-tools.sh osslsigncode`). The Authenticode slot is described in [ADR-0034](docs/adr/0034-authenticode-signing-of-windows-release-artifacts.md).
- The Linux updater archives no longer contain the Windows scripts (`install-windows.ps1`, `Set-ServiceEnvironment.ps1`); they are in the Windows archives only.
- Release builds omit the `devpg` build tag, so the embedded PostgreSQL (and its dependencies) is not linked. `myriarchd dev` in such a build needs `--dsn`; `make dev` and `make build` keep the tag. See `docs/development.md`.
- `ci/check-release-licenses.sh` (part of `make check-local`) runs `go-licenses` over the release builds against a license allowlist; exceptions are documented in `docs/development.md`.
- The UI uses system font stacks instead of bundled web fonts, so the embedded UI ships no font files.
- `IMAGE_VARIANT=release scripts/build-image-crane.sh` builds the server image without `devpg` and without the OpenTelemetry release fixtures (`/opt/myriarch/release-fixtures`); the default `dev` variant keeps both.
- The in-process LRU caches use the internal `internal/lru` package, so `github.com/hashicorp/golang-lru` is not a dependency.
- **Continuous integration.** GitHub Actions runs the gates of `ci/check-local.sh` as jobs (`.github/workflows/ci.yml`), with a platform matrix for the Go tests (Linux amd64 and arm64 with a PostgreSQL service and `-race`, macOS with `-race`, Windows without `-race`), the release rehearsal, a secret scan of the commits of a pull request and the script tests. The aggregate job `ci-ok` is the only required check. `.github/workflows/e2e.yml` runs the end-to-end smoke test on pull requests and the load run and the UI version update test nightly. Only GitHub-owned actions pinned to a commit SHA are used, the token is read-only and the CI jobs have no secret; a deployment job can read an environment secret only when `ci/workflow-secrets.txt` lists it, the job declares an `environment:` and the secret is passed as `KEY: ${{ secrets.NAME }}` in an `env:` ([ADR-0032](docs/adr/0032-continuous-integration-on-github-actions.md)).
- **Workflows gate.** `make check-local` has a gate `workflows`: `actionlint` (pinned in `ci/tools/actionlint`) and the policy check `ci/check-workflows.py`, which also verifies that every gate has a CI job and reads workflow files and local actions with the extension `.yml` as well as `.yaml`. The gates `go` (vet for macOS) and `helm` (schemas of Kubernetes 1.30.0 and 1.34.12) check more; `GO_TEST_RACE`, `GO_TEST_DEVPG`, `GO_TEST_PERF`, `HELM_KUBERNETES_VERSIONS` and `CHECK_LOCAL_STREAM` select variants. The render budget of the server (5000 agents in under 5 s) is asserted only by a run of its own without `-race` (`PERFTEST=1`, `GO_TEST_PERF`), not inside the parallel `go test ./...`, and applies to the median of three renders.
- **Workflow policy for Scorecard and releases.** The policy check allows one third-party action, `ossf/scorecard-action`, pinned to a commit SHA and only in `.github/workflows/scorecard.yml`, job `analysis` (rule R1). Rule R12 holds that workflow to the shape the OpenSSF Scorecard API requires for published results (push to `main` and a schedule, one job, only `uses:` steps from a fixed list, exactly the permissions `contents: read`, `actions: read`, `security-events: write` and `id-token: write`, no secrets or caches). Rule R13 prepares `.github/workflows/release.yml`: a trigger for pushed `v*` tags only, no caches or local actions, the literal environment `release`, a `guard` job that every job needs, no Node.js, Go, pnpm, npm, goreleaser, make or similar build tool in a job with a write scope, `id-token`, `attestations` or an environment, no `if:` that tests job status and no `continue-on-error` that would defeat `needs:`, no script on standard input or foreign `shell:` in a privileged job, and an approval before every privileged job ([ADR-0033](docs/adr/0033-openssf-scorecard-as-the-only-third-party-action.md), which amends [ADR-0032](docs/adr/0032-continuous-integration-on-github-actions.md)).
- **CodeQL, Scorecard and zizmor.** `.github/workflows/codeql.yml` runs CodeQL (`security-extended`) on pushes to `main`, on every pull request to `main` (forks and Dependabot included) and weekly. It analyses Go (a traced build for Linux, Windows and macOS, also with the `embedui` and `devpg` tags), JavaScript and TypeScript, Python and the workflows themselves. `.github/workflows/scorecard.yml` runs the OpenSSF Scorecard weekly and on pushes to `main`, publishes the result and uploads the findings to code scanning, in the shape that rule R12 requires. The write scopes of both jobs are reviewed in `ci/workflow-permissions.txt`. The `workflows` gate runs zizmor with the pedantic persona and `zizmor.yml`: offline in the local gate, with the online audits against github.com only in CI, and a file that zizmor cannot parse fails the gate. The new rule R14 of the policy check allows only ignore entries with a worded reason in `zizmor.yml` and in inline comments, and it rejects files that the check and a YAML parser would read differently (U+0085, U+2028, U+2029, control characters, a byte order mark, text that is not UTF-8). Dependabot now waits 7 days after a release before it proposes a version update; security updates are not delayed ([the security model](docs/security/model.md), `docs/development.md`).
- **Toolchain files.** `.node-version` pins the Node.js LTS release (24.21.0) for CI and local development; the `engines` of `web/` require Node.js 22.22.2, 24.15 or newer (`^22.22.2 || ^24.15.0 || >=26`). `pnpm format:check` (prettier) is part of the `web` gate and `make lint`, and `playwright-core` is a development dependency of `web/` for the UI smoke tests.
- **Dependency updates.** Dependabot (`.github/dependabot.yml`) now proposes weekly grouped updates for the GitHub Actions, the root Go module, the packages of `web/` and `website/` and the brand generator (`assets/brand/source`), and security updates for the CI tool modules (`ci/tools/*`); `docs/development.md`, "Dependency updates", says what each kind of pull request needs besides the update itself (the required DCO check passes Dependabot's commits as they are). The pins behind the open alerts are raised: Pillow 12.3.0 for the brand generator, which now needs Python 3.10 or newer (`BRAND_PYTHON` selects the interpreter), and the vulnerable packages of the CI tool modules and the website tooling. The stamp of a Go tool in `.cache/bin` now holds a digest of its `go.mod` and `go.sum`, so a raised requirement rebuilds the tool, also from a tool cache that CI restored from an older run (before, the old binary stayed until the tool version changed).
- **End-to-end test with the real supervisor.** `E2E_REAL=1 scripts/e2e.sh` downloads the upstream supervisor and `otelcol-contrib` of `OTELCOL_VERSION` for darwin and linux on amd64 and arm64 (previously darwin/arm64 only) and verifies both against the published SHA-256 on every run. With `E2E_REAL=1` or `E2E_UI=1` a missing prerequisite fails the run instead of skipping the step. `E2E_REAL_BASE_URL` replaces the download location.
- **Secret scan of commit ranges.** `SECRETS_SCAN_RANGE=<base>..<head> ci/secrets-scan.sh` scans the commits of a range with gitleaks.
- **Version source.** The file `VERSION` holds the next release tag without the `v` (for example `0.1.0-rc.3`), and `scripts/set-version.sh <version>` writes it together with every copy: the chart `version` and `appVersion`, `web/package.json`, `api/openapi.yaml`, the image tags of the production example and of the GitOps template, and the default image tag of the Compose quickstart; then it runs `make docs-gen` and `pnpm gen:api`. `ci/check-versions.sh` fails on drift (part of the `go` gate and `ci/check.sh`).
- **Release tag guard.** `ci/release/guard.sh` refuses a release tag that is malformed, lightweight, not on `main`, different from `VERSION` or one of its copies, without a `CHANGELOG.md` heading and entries (final tags) or without entries under "Unreleased" (rc tags), without a successful `ci-ok` check run, or against the Windows signing rule of `deploy/release/windows-signing.env` (a final tag with signing `off` needs the reviewed exception for exactly that tag).
- **Authenticode for Windows.** [ADR-0034](docs/adr/0034-authenticode-signing-of-windows-release-artifacts.md) decides how the Windows release files get Authenticode signatures: the SignPath Foundation is the target, an IV certificate with an HSM key in Google Cloud is the fallback (trigger, budget and privacy consequence are recorded), and the release workflow keeps no long-lived signing secret. Authenticode adds to the Sigstore signature of [ADR-0023](docs/adr/0023-keyless-release-signing.md) and never replaces it. The Windows files of the v0.1.0 release candidates are unsigned (candidates may ship with signing off), and those of v0.1.0 under a reviewed exception for exactly that tag; verify them with cosign before you run them ([the security model](docs/security/model.md)).
- **Release scripts.** `ci/release` holds the scripts of the release workflow ([ADR-0035](docs/adr/0035-release-workflow-with-keyless-signing-and-verification-before-publication.md)): `meta.sh` (the outputs of the guard job; it refuses a run whose `GITHUB_WORKFLOW_REF` is not `release.yml` of the project at the tag, which keeps the signing identity frozen), `artifact.sh` (one deterministic tar per artifact, unpacked only after its SHA-256 matches), `tools.sh` (builds the signing and the build tool set, and checks a set after the unpack), `stage-assets.sh` and `verify-dist.sh`, `images.sh`, `registry-login.sh`, `verify-blob.sh` (the one place that composes `cosign verify-blob`), `sign-checksums.sh`, `sign-image.sh`, `notes.sh`, `draft.sh`, `verify.sh` and `finalize.sh`. `ci/release/identity.env` holds the signing identity as data, and `ci/tests/release-scripts-test.sh` pins it to `internal/brand`, ADR-0029, the installers and `push-images.sh`.
- **Release asset list.** `deploy/release/assets.json` is the complete set of release files: 42 names, 40 built (`ci/release/stage-assets.sh` and `verify-dist.sh` check them against the goreleaser output; `make release-rehearsal` does this on every pull request) and two added by the signing job (`checksums.txt.sigstore.json` and `myriarch_<version>_provenance.intoto.jsonl`). `checksums.txt` lists exactly 39 of them.
- **Release notes.** `ci/release/notes.sh` renders `deploy/release/notes.md.tmpl` and the matching `CHANGELOG.md` section into the notes of a release: release candidate, final, unsigned-Windows and signed variants, the verification commands with the exact identity and the image digests.
- **Release workflow.** `.github/workflows/release.yml` builds, signs, verifies and publishes a release for every pushed `v*` tag: build code runs only in jobs without write scopes, the tools come as two sets (cosign, crane and gh are built first on a runner of their own and are the only tools of the privileged jobs), jobs exchange artifacts by ID with a SHA-256 check, two approvals of the environment `release` gate the signing slot and the publication, and smoke tests of the published release run in the same workflow ([ADR-0035](docs/adr/0035-release-workflow-with-keyless-signing-and-verification-before-publication.md)). `ci/tests/release-workflow-test.sh` pins its shape.
- **Smoke tests after publication.** `ci/release/smoke.sh` (subcommands `assets`, `linux`, `image-run` and `kind`) and `ci/release/smoke-windows.ps1` (modes `Assets` and `Install`) check a release the way a user does: anonymous downloads of the 42 release files and anonymous registry reads, the keyless signature of `checksums.txt` (exact and ADR-0029 identity, with a tampered copy as negative control), GitHub's release attestation, the build provenance and the image attestations, the installers from the verified archives in staging mode with the real collector, `docker run` of both images (user 65532, no shell, read-only), the Helm chart of the tag on a kind cluster (non-root pods, `/healthz`, `/readyz`, bootstrap sign-in) and the Windows files (version resources, Authenticode state, zip contents). The release workflow runs them after finalize ([ADR-0035](docs/adr/0035-release-workflow-with-keyless-signing-and-verification-before-publication.md)); `ci/tests/release-smoke-test.sh` tests them with stubs.
- **Enterprise mirror toolkit, keyless mode.** `contrib/enterprise-mirror/verify-release.sh --keyless --version X.Y.Z --dir|--base-url ...` verifies the keyless bundle `checksums.txt.sigstore.json` of the project's release with cosign 3.0.4 or newer against the exact identity of `release.yml` at the tag (and optionally every file against `checksums.txt`; `--trusted-root` for hosts without access to Sigstore), and `publish-mirror.sh --keyless --dir DIR --version X.Y.Z` verifies a downloaded release and uploads the host files unchanged, `checksums.txt` and the bundle last. The key-based mode is unchanged; `--keyless` and `--public-key` exclude each other.
- **Release fixture.** The keyless bundle of `checksums.txt` of `v0.1.0-rc.3` is a test fixture (`internal/updater/testdata/sigstore/myriarch_0.1.0-rc.3_*`): `myriarch-updater verify-bundle`, `install-linux.sh` and `install-windows.ps1` are tested offline, with the pinned trusted root, against the genuine release signature (accepted for 0.1.0-rc.3; refused for 0.1.0-rc.2, 0.1.0 and a tampered copy), and the real-cosign cases of the installer tests are required in CI.
